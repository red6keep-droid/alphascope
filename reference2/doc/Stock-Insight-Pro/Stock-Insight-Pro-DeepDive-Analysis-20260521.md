# Stock Insight Pro (1인용 퀀트 비서) - 코어 엔진 및 아키텍처 딥다이브 분석서

**분석 목적:** 현행 시스템(V6.3)의 한계점 파악 및 차세대 시스템(V7.0) 업그레이드를 위한 철저한 자가 진단 및 로직 복기
**작성일:** 2026년 5월 21일

이 문서는 "Stock Insight Pro"의 내부 뼈대인 퀀트 엔진, 데이터 파이프라인, 그리고 시스템 철학을 바닥부터 분해하여 분석합니다. 개발자가 작성한 코드가 실제 어떤 의도로 동작하는지, 데이터는 어디서 와서 어떻게 정제되는지를 투명하게 문서화하여 향후 업그레이드 방향성을 제시합니다.

---

## 1. 코어 시스템 철학: "Survival Over Alpha" (생존 최우선)

본 시스템은 월가의 헤지펀드나 HFT(고빈도 매매) 알고리즘과 다릅니다. 철저히 **"1인 직장인 스윙 트레이더"**의 수면을 보장하고 뇌동매매를 물리적으로 차단하기 위해 설계되었습니다.

*   **수학적 락(Lock) 메커니즘:** 인간의 "오를 것 같은데?"라는 직관을 배제합니다. 시스템이 `PANIC_SELL` 또는 `FAKE_REVERSAL`을 감지하면 매수 버튼 자체가 비활성화됩니다.
*   **결정론적(Deterministic) 평가:** AI(Gemini)는 결정을 내리지 않습니다. AI는 오직 백엔드 퀀트 엔진이 수학적으로 산출한 `Risk Penalty`와 `Action Zone`을 받아, 사용자에게 **"설명(Announce)"**하는 역할만 수행하도록 권한이 엄격히 분리되어 있습니다.
*   **Actionable Order (예약 매매):** 시차 문제를 극복하기 위해, 실시간 차트 모니터링 없이 "오늘 밤 $145.30에 1차 익절 예약 매도"와 같은 확정적 숫자를 산출합니다.

## 2. V6.3 핵심 퀀트 엔진 딥다이브 (`stockRiskEngine.ts`)

모든 매매의 심장부인 리스크 엔진은 5개의 모듈(5-Rule Budget)로 구성되며, 각 모듈이 감점(Penalty)을 누적하는 구조입니다.

### 2.1 국면(Regime) 식별기
주가 이평선(SMA)과 거래량, 변동성(VIX)을 조합해 시장의 상태를 5가지로 규정합니다.
1.  **`NORMAL`:** VIX < 25, 추세가 안정적인 상태.
2.  **`VOLATILE`:** VIX > 30 이거나 ATR이 평소 대비 크게 팽창한 구간.
3.  **`PANIC_SELL`:** 주가가 20일선(SMA20)을 -5% 이상 하회하고, 거래량이 20일 평균 대비 150% 폭증할 때. (항복 구간)
4.  **`PANIC_BUY`:** 극단적 과매수 (RSI > 80).
5.  **`FAKE_REVERSAL` (가짜 반등 / 함정):** 주가가 20일선을 돌파했지만, **거래량이 평균의 70% 미만일 때**. (세력의 물량 떠넘기기로 간주하여 매수를 가장 강력하게 차단하는 핵심 룰).

### 2.2 Penalty Accumulation (위험도 산출 로직)
엔진은 `calculateStockRisk` 함수를 통해 `penaltyPercent` (0~100%)를 산출합니다.
*   **Data Integrity Penalty:** 주가, 거래량 등 필수 데이터가 누락되거나 지연(15분 이상)되면 신뢰도가 차감되며 최대 100%의 페널티를 부여해 매매를 원천 봉쇄합니다.
*   **Macro Penalty:** VIX 35 초과 시 +60%, `PANIC_SELL` 시 최소 50%의 베이스 페널티가 부여됩니다.
*   **Volatility Penalty:** 5일 ATR이 90일 ATR 대비 1.5배 이상 팽창하면(Drift) +20% 가중.
*   **Threshold (임계치):** 총 페널티가 **45%**를 초과하면 시스템은 `NO TRADE (철저히 관망하세요)` 액션 존을 발동하고, 즉시 손절/익절 대기 모드로 전환됩니다.

## 3. 원천 데이터 파이프라인 (Data Architecture)

유지비용 0원을 달성하면서도 데이터 무결성을 지키기 위한 아키텍처입니다. 로직은 주로 `server.ts`의 프록시 라우터들에 집중되어 있습니다.

### 3.1 Data Sources & Usage
*   **Yahoo Finance (`yahoo-finance2` 라이브러리):** 
    *   사용처: 실시간/지연 주가, 과거 1년치 차트 데이터(`historical()`), 옵션 체인, 재무/종목 정보.
    *   한계 및 우회: 잦은 HTML/캡챠 차단. 이를 방지하기 위해 `historical()` 실패 시 `chart()` API로 우회하는 `safeHistorical` 래퍼 함수를 구현했습니다.
*   **Alpha Vantage:**
    *   사용처: 재무제표 요약, 기본 정보(`OVERVIEW`).
    *   방어 로직: 무료 티어의 "분당 5회" 제한을 피하기 위해 다중 API 키(Array) 기반의 **Smart Key Rotation**과 `avServerQueue`를 통한 1.2초 지연 큐잉 시스템을 독자적으로 구축했습니다.
*   **Twelve Data / Finnhub:**
    *   사용처: 일봉 지표, 기술적 분석 데이터 및 실시간 뉴스. (Alpha Vantage 백업용)
*   **FRED (연방준비은행):**
    *   사용처: 장단기 금리차(T10Y2Y), 신용 스프레드(BAMLH0A0HYM2), 기준금리 등 매크로 지표.
*   **FINRA (공매도 및 다크풀 스크래핑):**
    *   특이점: 잦은 403 (WAF 봇 탐지) 차단 발생.
    *   해결책: 지수적 백오프(Exponential Backoff)를 적용한 `fetchFINRAWithRetry` 함수와, 완전히 실패할 경우 **T-2일(어제/그제) 로컬 캐시 데이터(`finraCache`)를 반환**하도록 하여 엔진 에러를 방어합니다. "초단기 데이터보다 시스템의 안정적인 실행이 낫다"는 철학이 반영되었습니다.

### 3.2 로컬 캐싱 및 백그라운드 스케줄러 (`cron`)
*   **`0 7 * * *` (아침 7시):** `fetchMorningMacroData` 함수가 금, 원유, 비트코인, 국채금리 등 글로벌 자금 흐름을 선제적으로 수집해 Firestore에 저장합니다.
*   **`0 5 * * *` (새벽 5시):** 주요 10개 종목의 시세 스냅샷을 백그라운드에서 다운로드하여 일일 데이터 로딩 속도를 향상시킵니다.
*   **.ai_cache.json:** Gemini API 비용 절감을 위해 동일한 프롬프트 해시값에 대해 24시간 동안 응답 텍스트를 파일 시스템에 캐싱합니다.

## 4. 백테스트 검증 시스템 딥다이브

"이 엔진이 실제로 과거의 함정을 피했는가?"를 증명하는 로직(`server.ts` -> `/api/v3-backtest/:symbol`).

### 4.1 핵심 구조
과거 250일(약 1년) 치 주가 배열을 순회(`for loop`)하며, 당시 시점의 지표를 완벽히 재현합니다.
*   **미래 참조(Look-ahead) 방지:** 반복문 인덱스 `i` 이전의 데이터만을 슬라이싱(`quotes.slice(0, i + 1)`)하여 그 시점만의 RSI, ADX, SMA, ATR을 동적으로 계산합니다. (V7.0을 위해 최근 업데이트 됨)
*   **가상 매매 체결 (Virtual Execution):** 
    *   엔진이 `BUY`를 뱉고 잔여 현금이 있으면 **1차 분할 매수**가 기록됩니다.
    *   매수 이후, 당시 ATR 기반으로 동적 산출된 **1차 목표가, 2차 목표가, 손절가** 라인이 설정되며 주가가 이를 터치하면 자동으로 `SELL`이 기록됩니다.
    *   만약 목표가 도달 전, 엔진 페널티가 45%를 넘어 `NO TRADE`로 바뀌면 **엔진 강제 매도 (Survival Lock)** 가 실행됩니다.

### 4.2 UI 로그 시각화
백테스트 루프에서 쌓인 배열(`history.push`)은 React 컴포넌트(`ScenarioBoard.tsx`)로 전달되어 시각화됩니다.
*   단순히 매매 결과를 렌더링하는 것을 넘어, **[결정 사유]**란에 매매 당일의 `시장 레짐`, `엔진 신뢰도`, `VIX 수치`, `핵심 지표(RSI, ADX, ATR Drift)`를 스냅샷 형태로 박제하여 사용자가 AI의 결정을 투명하게 검증(Audit)할 수 있도록 합니다.

## 5. 차세대 (V7.0) 업그레이드를 위한 한계점 및 제언

현재 시스템을 분석한 결과 도출된 개선 포인트입니다.

1.  **FINRA 공매도 데이터 취약성:**
    *   현상: `FINRA 403` 봇 차단이 빈번하게 발생하여 T-2 캐시 데이터에 의존하는 빈도가 높습니다.
    *   제언: 무료 프록시나 외부 서버리스 펑션(GCP Cloud Functions 등 IP 로테이션 가능 환경)으로 크롤러만 분리하는 마이크로서비스 아키텍처(MSA) 도입이 필요합니다.
2.  **백테스트 엔진 속도 (N^2 이슈):**
    *   현상: 250일 루프 안에서 배열을 매번 슬라이싱(`slice`)하여 지표를 재계산하는 방식은 요청 시 수 초의 지연을 유발합니다.
    *   해결 (최근 부분 수정됨): 지표(`RSI`, `ADX`)를 루프 바깥에서 O(N)으로 전체 배열에 대해 1회 선행 계산(Pre-calculate)한 뒤, 인덱스로 매핑하여 가져오는 구조를 도입했습니다. 향후 모든 커스텀 지표도 이 방식으로 전환해야 합니다.
3.  **포트폴리오 스토리지 의존성:**
    *   현재 보유 주식(`myStocks`)과 가상 계좌 상태가 로컬 스토리지(`zustand persist`)와 Firestore에 혼재되어 동기화 타이밍 이슈(Race condition)가 존재할 수 있습니다. V7에서는 Firestore를 SSOT로 완전히 일원화하는 작업이 필요합니다.
4.  **AI 컨텍스트 윈도우 초과 (Over-prompting):**
    *   현재 `SYSTEM_PROMPT`가 매우 길고 엄격합니다. 향후 Gemini 모델이 업데이트되며 토큰 제한에 걸리거나 락(Lock) 지시를 무시할 가능성이 있습니다. V7에서는 프롬프트를 모듈화(Macro Prompt, Stock Prompt, Portfolio Prompt)하여 조립하는 방식(RAG 또는 Chain)의 도입을 고려해야 합니다.
