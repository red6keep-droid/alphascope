# GitHub Actions 정시 실행 — AlphaScope 방법

GitHub Actions 의 `schedule`(cron)은 **정시를 보장하지 않는다.** 부하가 높으면 몇 시간 늦거나 통째로 빠진다.
"30분마다 회차가 연속으로 빠지는" 증상은 설정 문제가 아니라 GitHub cron 의 평소 모습이다.

AlphaScope 실측 (2026-10-21 10:30 ~ 10-22 10:30 KST, GitHub cron 만 쓰는 워크플로):

| 워크플로 | 설정 | 기대 회차 | 실제 회차 |
|---|---|---|---|
| update.yml (시세) | 15분마다 | 96 | **7** |
| news.yml (뉴스) | 2시간마다 | 12 | **4** |

2026-10-13 에는 데일리 · 트럼프 · NVDA 리포트 예약이 하루치 전부 오지 않았다. 그래서 정해진 시각에 꼭 돌아야 하는 작업은
**바깥 예약기가 GitHub 에 "지금 실행해"(workflow_dispatch)를 걸고, GitHub cron 은 예비로 남기는** 방식으로 바꿨다.

---

## 구조

```
Cloudflare Worker (Cron Trigger, 무료)
   │  정해진 시각에 POST /repos/{owner}/{repo}/actions/workflows/{file}/dispatches
   │  body: {"ref": "main", "inputs": {"scheduled": "true"}}
   ▼
GitHub Actions 워크플로 (workflow_dispatch + schedule 둘 다 받음)
   ├─ scheduled=true 로 온 실행 = 예약 실행과 똑같이 취급 (자동 게시 등)
   ├─ concurrency 그룹 → 한 번에 하나만
   └─ 맨 앞에서 "이미 했나?" 확인 → 했으면 나머지 단계 건너뜀
GitHub cron (예비) — 같은 시각 근처에 그대로 둔다
```

둘 다 도는 날도 문제없다. 뒤에 온 실행이 "이미 함"을 보고 끝난다.

## 네 가지 핵심

1. **바깥 예약기가 workflow_dispatch 를 건다.** Cloudflare Worker · Google Cloud Scheduler 어느 쪽이든 된다.
   중요한 건 도구가 아니라 "GitHub cron 하나에 기대지 않는다"는 점이다.
2. **`scheduled` 입력으로 예약 실행을 구분한다.** 사람이 손으로 돌린 실행(시험 · 재실행)과 예약 실행을 나눠야
   "예약일 때만 자동 게시" 같은 규칙을 지킬 수 있다.

   ```yaml
   on:
     schedule:
       - cron: '0 22 * * *'          # 예비
     workflow_dispatch:
       inputs:
         scheduled:
           description: '외부 예약기용 — 스케줄 실행과 똑같이 동작 (사람은 끄고 쓴다)'
           type: boolean
           default: false
   env:
     IS_SCHEDULED: ${{ github.event_name == 'schedule' || inputs.scheduled == true }}
   ```
3. **실행은 몇 번 와도 결과가 한 번이어야 한다(멱등).** 리포트는 "오늘 글이 이미 있나"를 보고 건너뛴다(`check_published.py`).
   수집이라면 "이미 받은 영상 · 기사는 다시 받지 않음"이 같은 역할이다. 그리고 `concurrency` 로 겹쳐 돌지 않게 한다.

   ```yaml
   concurrency:
     group: collect
     cancel-in-progress: false   # 돌고 있는 실행을 끊지 않고 뒤에 줄 세운다
   ```
4. **토큰은 최소 권한.** GitHub fine-grained token — 그 저장소 하나만, 권한은 **Actions: Read and write** 하나만.
   예약기 쪽 비밀값(Worker secret · Secret Manager)에만 넣고 코드 · 문서에는 쓰지 않는다.

## Cloudflare Worker 로 하는 법 (AlphaScope 가 쓰는 것)

무료 플랜으로 충분하다. cron 트리거는 계정당 5개지만, **트리거 하나가 여러 시각 · 여러 워크플로를 맡을 수 있다** —
Worker 가 깨어날 때마다 "지금 시각에 할 일" 표를 보고 건다.

`wrangler.toml`

```toml
name = "collect-cron-trigger"
main = "src/index.js"
compatibility_date = "2026-10-01"
workers_dev = false            # HTTP 주소 없음 — cron 으로만 돈다

[triggers]
crons = ["5,25,35 * * * *"]   # UTC. 아래 표의 분(分)을 모두 덮는 깨어남 격자
```

`src/index.js` — 시각은 **현지 시각(Asia/Seoul)** 으로 판단한다. 미국장에 묶인 작업이면 `America/New_York` 로 판단해야
서머타임이 바뀌는 날(11월 첫 일요일)에도 장 마감 기준 시각이 유지된다 (AlphaScope 는 뉴욕 시각으로 판단).

```js
const REPO = "owner/repo";
const TZ = "Asia/Seoul";

function localHM(d) {
  const p = Object.fromEntries(new Intl.DateTimeFormat("en-US", {
    timeZone: TZ, hour12: false, hour: "2-digit", minute: "2-digit",
  }).formatToParts(d).map((x) => [x.type, x.value]));
  return `${p.hour}:${p.minute}`;
}

// 예: 필수 채널 07:35 ~ 11:35 30분마다, 일반 채널 21:25 ~ 07:25 매시
function due(hm) {
  const [h, m] = hm.split(":").map(Number);
  const jobs = [];
  const t = h * 60 + m;
  if (t >= 7 * 60 + 35 && t <= 11 * 60 + 35 && (m === 5 || m === 35)) jobs.push("collect.yml");
  if (m === 25 && (h >= 21 || h <= 7)) jobs.push("collect.yml");
  return [...new Set(jobs)];
}

async function dispatch(workflow, token) {
  const res = await fetch(`https://api.github.com/repos/${REPO}/actions/workflows/${workflow}/dispatches`, {
    method: "POST",
    headers: {
      Authorization: `Bearer ${token}`,
      Accept: "application/vnd.github+json",
      "X-GitHub-Api-Version": "2022-11-28",
      "User-Agent": "collect-cron-trigger",
    },
    body: JSON.stringify({ ref: "main", inputs: { scheduled: "true" } }),
  });
  if (res.status !== 204) throw new Error(`${workflow}: HTTP ${res.status} ${await res.text()}`);
}

export default {
  async scheduled(event, env) {
    const jobs = due(localHM(new Date(event.scheduledTime)));
    if (!jobs.length) return;
    const r = await Promise.allSettled(jobs.map((w) => dispatch(w, env.GITHUB_TOKEN)));
    const failed = r.filter((x) => x.status === "rejected").map((x) => x.reason.message);
    if (failed.length) throw new Error(failed.join("\n"));   // Cloudflare 대시보드 로그에 남긴다
  },
};
```

배포:

```
npx wrangler login
npx wrangler secret put GITHUB_TOKEN   # fine-grained token 붙여넣기 (화면 · 문서에 남기지 않는다)
npx wrangler deploy
```

확인: Cloudflare 대시보드 → Workers → (이름) → Logs / Cron Events. 그리고 GitHub Actions 실행 목록에서
`workflow_dispatch` 실행이 정시에 생기는지 본다.

주의:
- 워크플로에 `scheduled` 입력이 들어간 커밋이 **기본 브랜치에 먼저 올라가야** 한다. 그 전에는 GitHub 가
  "Unexpected inputs"(422)로 거부한다.
- 시각을 바꾸면 ① Worker 의 표 ② `crons` 깨어남 격자 ③ 워크플로의 예비 cron 셋을 같이 맞춘다.

## Google Cloud Scheduler 를 쓴다면

같은 구조로 된다. 차이만 적는다.

| | Cloudflare Worker | Google Cloud Scheduler |
|---|---|---|
| 시간대 | 코드에서 `Intl` 로 판단 | 작업마다 시간대 지정 가능 |
| 작업 수 | 트리거 하나로 여러 시각 · 워크플로 | 시각 패턴마다 작업 하나 (무료 3개 범위) |
| 준비 | Cloudflare 계정 | 그 GCP 프로젝트에 결제 계정 연결 필요 |
| 토큰 보관 | Worker secret | Secret Manager 또는 작업의 HTTP 헤더 |

Firebase 프로젝트가 이미 있으면 Cloud Scheduler 도 좋은 선택이다. 시간표가 "07:35~11:35 30분마다"와
"21:25~07:25 매시" 두 패턴이면 작업 2개로 덮인다.

## 우리도 아직 남은 것

AlphaScope 도 처음엔 리포트(데일리 · 트럼프 · NVDA)만 Worker 로 옮겼고, 고빈도 수집(update.yml 15분 · news.yml 2시간)은
GitHub cron 만 썼다 — 위 실측이 그 결과다. 2026-10-22 에 같은 Worker 에 붙였다 (`crons = ["*/15 * * * *"]` 하나로
리포트는 뉴욕 시각 표, 수집은 UTC 간격으로 판단). 트리거를 늘리지 않고 표만 늘리면 된다.
