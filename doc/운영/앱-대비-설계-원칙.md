작성: 2026-11-22 · 모든 새 기능에 적용 · CLAUDE.md `앱 대비` 절이 이 문서를 가리킨다.

사용자 2026-11-22: "블로그는 그냥 앱을 위한 징검다리라고 보면 돼. 블로그가 어느 정도 되면 앱을 출시할 거거든. 그래서 우리 도메인 이름도 앱(newfact.app)이야. 앱까지 고려해야 된다는 것을 특정한 기능에서도 문서에 철저하게 기록해. 근데 지금 하는 거랑 앱 만드는 거랑 완전 다르다고 판단되면 안 해도 돼."

## 1. 한 줄 원칙

**화면(블로그 HTML)과 데이터 · 기능(주소로 부르는 JSON · API)을 나눈다.** 블로그는 그 데이터를 그리는 화면 하나이고, 앱은 같은 데이터를 그리는 두 번째 화면이다. 블로그 안에서만 동작하는 방식으로 데이터를 만들거나 저장하지 않는다.

앱 대비 때문에 지금 일이 크게 늘거나 블로그가 불편해지면 하지 않는다(사용자 "완전 다르면 안 해도 돼"). 그때는 이 문서 4절 기록에 "앱 때 할 일"로 적고 넘어간다.

## 2. 새 기능마다 확인할 것

| 확인 | 앱 대비로 하는 것 | 하지 않는 것 |
|---|---|---|
| 데이터 | 주소로 부를 수 있는 JSON 파일 · API(Cloudflare Pages · R2 · Worker) | Blogger 글 HTML 안에만 숫자를 박아 두기(앱이 못 읽음) |
| 열쇠 · 이름 | 종목 코드 · 영문 주소 이름(`stock-NVDA` · `forecast-nvda-2026q3` · `market-kr`)처럼 **Blogger 밖에서도 뜻이 통하는 열쇠** | Blogger 글 번호(숫자 id)를 데이터 열쇠로 쓰기 — 앱에는 그 번호가 없다 |
| 로그인 | Firebase 구글 로그인(앱 SDK 있음) → 서버는 **ID 토큰을 `Authorization` 머리말**로 받는다 | 쿠키 · 블로그 도메인에 묶인 세션 |
| 쓰기 · 규칙 | 서버(Worker)가 검사(하루 상한 · 링크 막기 · 권한) — 어느 화면에서 와도 같은 규칙 | 브라우저 JS 만 믿는 검사 |
| 캐시 | 서버 쪽 = Cloudflare 캐시(방문자 수에 안 묶임) · 화면 쪽 = 브라우저는 HTTP 캐시 · localStorage, 앱은 기기 저장소에 같은 JSON 을 저장 | 브라우저 localStorage 에만 있어야 동작하는 기능(앱에서 다시 만들어야 함) |
| 개인 상태(내 표 · 내 종목 · 알림 설정) | 서버에 저장하고 로그인한 사람에게 준다 → 블로그 · 앱이 같은 상태 | 기기 한 곳에만 저장(기기를 바꾸면 사라짐). 기기 저장은 "빠르게 보이기용 사본"으로만 |
| 그림 · 스티커 | 공개 주소(Pages) 하나 — 앱도 같은 주소 | Blogger 이미지 서버에만 올리기 |
| 링크 · 공유 | `https://www.newfact.app/…` 주소 하나 → 앱이 깔린 폰은 앱으로 열리게(유니버설 링크 · 앱 링크, 확인 파일은 Cloudflare 하위 주소) | 앱 전용 주소를 따로 만들기 |
| 알림 | 알림을 보낼 "일"(답글 달림 · 신고 처리)을 서버 기록으로 남긴다 → 앱 때 푸시(FCM)로 연결 | 이메일 · Slack 에만 묶기 |
| 한도 | **하루 방문객 10만 기준**으로 처음부터(앱 사용자도 같은 서버를 부른다) | 방문자 수에 묶이는 읽기(브라우저가 Firestore 를 바로 읽는 것 등) |

## 3. 앱 출시 때 생기는 일 (미리 알아 둘 것)

- **애플 로그인**: 앱스토어는 구글 같은 외부 로그인을 쓰면 애플 로그인(또는 같은 수준의 개인정보 보호 로그인)도 넣으라고 한다(App Store 심사 지침 4.8). Firebase 로그인에 애플을 더하면 서버(토큰 확인)는 그대로다.
- **앱 링크 확인 파일**: Blogger 는 `/.well-known/` 에 파일을 못 올림 → Cloudflare 하위 주소(도메인-구입.md 5절).
- **회원 등급 · 결제**: 회원-내-종목-기획.md 8-1 — 앱 때 설계.
- **개인정보처리방침**: 앱이 받는 것(기기 알림 토큰 등)을 더한다.
