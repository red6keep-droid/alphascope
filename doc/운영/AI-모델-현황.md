| `nvidia-deepseek` | NVIDIA DeepSeek V4.1 Flash | 사고 끔 | — | 예비 중 서술 품질 1위(10-14) | **운영에서 뺐다**(10-21, 무료 엔드포인트는 개발 · 시험 전용 약관). `LLM_ALLOW_NVIDIA=1` 로컬 실험만 |
| `nvidia-gptoss20` | NVIDIA gpt-oss-20b | 번역 전용 | — | 번역 5초 | 같은 이유로 운영 제외 |

- Groq 두 모델은 **같은 키**, 한도는 **모델마다 따로**. **하루 토큰 한도(TPD) 20만** — gpt-oss 는 10-26 01:25 UTC 실행에서 `tokens per day (TPD): Limit 200000, Used 199813` 으로 확인. **하루 요청 1,000회보다 하루 토큰 20만이 먼저 찬다** (호출당 5 ~ 8K 토큰이면 하루 25 ~ 40회).
- Groq 429 오류 원문 세 종류 (10-26 확인 — 앞 160자만 남기던 로그에서 안 보였다. 지금은 `_groq_reason` 이 이 부분만 남긴다):
  - `tokens per minute (TPM): Limit 8000, Used …, Requested …. Please try again in 23.52s` → 기다리면 풀림 (자동 재시도 1회)
  - `output tokens per minute (OTPM): Limit 1000, Requested 2184` → 기다려도 잘 안 풀림 (바로 다음 단계)
  - `tokens per day (TPD)` · 하루 요청 → 그날은 안 됨 (바로 다음 단계)
- 413 `Request too large` 는 요청 하나가 분당 8,000토큰보다 큰 것 — 몇 번을 보내도 거절.
- **Qwen 규칙 (10-26 실측)**: Groq 는 요청마다 "예상 출력"(= `max_completion_tokens`, 또는 직전 호출 출력량)을 잡고, 그것이 1,000을 넘으면 **몇 분을 쉬어도** OTPM 429 로 거절한다
  (상한 8,000 → "Requested 2184 · 3013", 상한 1,500 → "Requested 1500"). 직전 출력이 1,000 이하여야 다음 호출이 받힌다.
  → 출력 상한을 1,000으로 두고 **답이 1,000토큰 안에 드는 크기로만** 보낸다. 뉴스 4건(출력 817 ~ 905)은 62초 간격 3연속 성공, 5건(약 1,100)은 두 번째부터 거절.
  답이 1,000을 넘으면 잘려 JSON 이 깨지고 다음 단계로 넘어간다. 기준: 뉴스 기사당 약 210 · 인용 추출 묶음당 약 50 · 카드 요약 장당 약 80토큰.

## 2. 예비 사슬 (CHAINS)

NVIDIA 단계는 운영에서 자동으로 빠진다(아래 "실제 순서"가 운영 기준).

| 사슬 | 실제 순서 (운영) | 쓰는 곳 | 왜 이 순서 |
|---|---|---|---|
| `json` | flash → lite → Qwen → gpt-oss | NVDA 분류 · 서술, 트럼프 분류 · 서술 | 독자 글 품질 우선. Groq 는 긴 프롬프트면 413 |
| `json-daily` | flash → lite → Qwen → gpt-oss | 미국 증시 데일리 서술 | (원래 DeepSeek 이 lite 앞 — NVIDIA 제외로 lite 가 2순위) |
| `json-gemini` | flash → lite | NVDA · 트럼프 재분류 (예비 모델이 임시로 단 라벨을 Gemini 로 다시) | 정식 라벨은 Gemini 만 |
| `json-backup-first` | **Qwen → gpt-oss → lite** | 인물 레이더 인용 추출, Media Daily 서술 | 새 기능은 예비 먼저 (10-19). 출력이 짧은 일 |
| `json-oss-first` | **gpt-oss → Qwen → lite** | 인물 레이더 분류 · 카드 요약 | **10-26 신설** — 출력 2천 토큰이 Qwen 출력 한도에 걸려서 |
| `news` / `news-alt` | Qwen → gpt-oss → lite / gpt-oss → Qwen → lite | 공용 뉴스 처리(news_store): 홈 뉴스 · 데일리 뉴스 · 종목 레이더 | 배치마다 번갈아 — 모델마다 60초 기다림을 반으로 (10-25). **10-26: Qwen 차례는 4건, gpt-oss 차례는 10건** · 48시간 넘은 새 기사는 AI 안 보냄 · 시간 예산 30분 |
| `comment` | gpt-oss → Qwen → lite → flash | 블로그 댓글 답글 | 댓글 한 건에 Gemini 를 쓰지 않게, flash 는 맨 뒤 |
| `translate` · `json-lite` | — | **지금 쓰는 곳 없음** (news 사슬로 옮김) | 정리 대상 |

공통 동작 (`llm_chain.LLMPool`):
- 한 단계가 실패하면(한도 · 과부하 · 형식 오류 · 검사 탈락) 다음 단계로. 전부 실패면 `RuntimeError` → 파이프라인마다 대체 처리(원문 제목 · 파이썬 문장 · 다음 실행이 이어받기).
- Gemini: 분당 한도 → 60초 쉬고 재시도, **하루 한도 → 그 실행 동안 그 모델 버림**, 503 → 3 · 6초 뒤 재시도.
- Groq (10-26부터): 분당 입력 한도 429 → 알려 준 시간(최대 150초) 기다렸다 1회 더. 출력 한도 → 바로 다음 단계. **하루 한도(TPD) → 그 실행 동안 모든 사슬에서 그 모델을 건너뜀**(`_day_out`, Gemini PerDay 와 같은 원칙). 뉴스 처리는 그때 남은 기사를 Qwen 크기(4건)로 나눈다(`pool.first_step`).
- 답한 모델은 `pool.last_model` 로 기록 (`groq:` · `gemini-…`) — 예비 모델이 단 라벨은 콜론이 있어 나중에 재분류 대상이 된다.
- 숫자가 들어간 서술은 `fact_check.py` 로 원문 숫자와 대조 (gpt-oss 방향 오류 이후).

## 8. 다시 재는 법

1. 로그 모으기: `gh run list --workflow <파일> --created ">=날짜"` → `gh run view <id> --log` 를 임시 폴더에.
2. 단계별 성공률: 로그의 `groq-qwen 3/8 · groq 2/4 · gemini-lite 1/1` 줄(`usage_line`)을 실행마다 모은다.
3. 실패 이유: `실패 — ` 뒤 문구. 10-26부터 Groq 는 `tokens per minute (TPM)` · `output tokens per minute (OTPM)` · `per day` 가 그대로 찍힌다.
4. Groq 남은 하루 요청: 아무 호출의 응답 헤더 `x-ratelimit-remaining-requests` (키는 화면 · 로그에 찍지 않는다). 하루 토큰은 헤더에 없다 — 429 `tokens per day (TPD) … Used N` 문구로만 보인다.
5. Gemini 하루 한도: AI Studio 할당량 화면 (`GenerateRequestsPerDayPerProjectPerModel`).
6. 운영 기록 콘솔(ops-console)은 `USAGE` · 사건을 실행 끝에 KV 로 남긴다 — 로그 대신 그쪽을 봐도 된다.
