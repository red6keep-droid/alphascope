# 트럼프 SNS 트렌드 리포트 — 기획

Trump의 Truth Social 게시물을 매일 수집해 구조화하고, 발언을 **이벤트 단위**로 묶어 3일·7일·30일·90일 누적 경향과
시장의 **초과 반응(abnormal return)** 을 결합해 **Trump Daily Market Trend Report**를 만든다.
기존 [데일리 리포트 파이프라인](데일리-리포트-파이프라인.md)의 설계 원칙 — 숫자는 파이썬이, 문장은 Gemini가 — 을 그대로 따른다.

작성일: 2026-09-15 · 개정 1: 이벤트 클러스터링 · 초과 반응 · 노이즈 필터 · Gemini 호출 유의점 ·
개정 2 (2026-09-15): 개발 전 확정값 5개 · **무료 플랜 기준 가격 데이터 재검토** ·
상태: **구현 1차 완료 (그림자 모드)** — 코드: [`experiments/trump-trend/`](../experiments/trump-trend/) · 기획서와 다른 점은 그쪽 README에 표로 정리

①단계 확인 결과 (2026-09-15): CNN archive는 `https://ix.cnn.io/data/truth-social/truth_archive.json` 하나(약 20MB)에
2022-02부터 전체 게시물(약 3만 6천 건)이 UTC 타임스탬프로 들어 있다. 180일 백필 조건을 충족하고, 90D 변화율 계산이 가능하다.
필드는 `id · created_at · content · url · media · replies_count · reblogs_count · favourites_count`. 본문 없는 글이 약 20%, 사전 필터 노이즈는 전체의 약 44%.

②③④ 진행 결과 (2026-09-15): 90일 백필 완료(1,295건 분류, 검증 탈락·실패 0), 이벤트 206개.
④ 50개 수동 검증 일치율 94% (사전 필터 100%, Gemini 분류 91%, 불일치는 전부 한 단계 높게 매긴 쪽).
구현 중 확인된 설계 보정 — subtopic 표기 정규화, 자기 재게시(`RT @realDonaldTrump…`) 노이즈 처리,
일 단위 반응 통계에서 같은 거래일 이벤트를 관측 하나로 합침(N 과대 방지). 상세는 `experiments/trump-trend/README.md` 검증 기록.

이 프로젝트의 핵심은 "Trump가 무슨 말을 했는가"가 아니다.
**"최근 발언 패턴이 무엇으로 이동하고 있으며, 과거 유사 발언 이후 시장에서 어떤 반응이 반복됐는가"** 다.
승부처는 AI가 얼마나 잘 쓰느냐가 아니라 **1~3개월 뒤 쌓인 이벤트 데이터를 얼마나 신뢰할 수 있느냐**다.

| 항목 | 내용 |
| --- | --- |
| 목표 | Trump SNS 발언 → 분류 → 이벤트 묶기 → 누적 트렌드 → 시장 초과 반응 통계 → 일간 리포트 |
| 데이터 소스 | 1순위 CNN Truth archive (5분 갱신 JSON/CSV/Parquet) · 2순위 Trump's Truth (HTML) |
| 가격 데이터 | **MVP는 일봉** (기존 yfinance 수집기 재사용, 키 불필요) · 분 단위는 무료 API 키 1개로 백필 가능한 경로 확보 후 |
| 저장 | SQLite (`trump.db`) + 일별 Parquet 원본 |
| Gemini 담당 | 게시물 **분류**(주제·방향·강도·시장 관련도)와 리포트 **서술**. 시장 영향 판단은 하지 않는다 |
| 파이썬 담당 | 중복 제거 · 노이즈 표시 · 이벤트 클러스터링 · 종목 매핑 · 트렌드 점수 · 이벤트 스터디 · 통계 |
| 실행 | 매일 1회, 처음엔 Windows 작업 스케줄러 → 안정화 후 GitHub Actions |
| 비용 | **전 구간 무료 플랜으로 구현 가능.** 9절에 서비스별 점검표 |
| 원칙 | 새 게시물만 저장·분석한다. 시장 영향은 가격으로 계산한다. 인과를 단정하지 않는다 |

```
CNN Truth Archive / Trump's Truth
        ↓
매일 1회 Python 실행 — 새 게시물만 저장 (id 비교)
        ↓
사전 필터 — 본문 없는 글·단순 인사 등에 noise_reason 표시
        ↓
Gemini 분류 (배치) — Topic · Direction · Intensity · Market Relevance
        ↓
Python — 매핑 규칙으로 영향 종목 산출 (rule_id 기록)
        ↓
Python — 이벤트 클러스터링 (같은 topic+target, 60분 이내 → event_id, 방향·강도 재계산)
        ↓
Python — 3D / 7D / 30D / 90D 집계 (같은 길이끼리 비교) · Trend Score (가중합)
        ↓
Python — 이벤트 스터디 (MVP: 당일·익일 종가 · SPY 대비 초과 반응 · confounded 제외)
        ↓
Gemini 서술 — 집계 JSON을 문장으로 ("반응이 관찰됐다", 인과 단정 금지)
        ↓
Trump Daily Market Trend Report
```

## 0. 먼저 알아둘 것 — 데이터 확보의 전제

Truth Social을 **직접 크롤링하지 않는다.** 두 가지 이유다.

1. TMTG(Trump Media & Technology Group)는 2026년 8월부터 **공식 유료 Truth API**를 제공하고 있고,
   무단 스크래핑에 대해 약관 위반을 문제 삼고 있다. ([Reuters][2])
2. 이미 공개 아카이브가 존재한다. `Trump's Truth`(trumpstruth.org)는 게시물을 지속 아카이빙하고 있고,
   2026-09-13 게시물까지 갱신된 상태다. ([Trump's Truth][1])

따라서 **개인용 리포트 단계에서는 공개 아카이브 데이터를 낮은 빈도(하루 1회)로 수집하는 구조부터 시험**한다.
상업적 이용이나 실시간성이 필요해지면 그때 공식 API를 검토한다.

## 1. 데이터 소스

### 1순위 — CNN Truth archive

GitHub의 `stiles/trump-truth-social-archive` 프로젝트는 원래 Python + GitHub Actions로 게시물을 수집했으나,
현재는 **5분마다 갱신되는 CNN archive의 JSON / CSV / Parquet 데이터**를 안내하고 있다. ([GitHub][3])

```
CNN Truth Archive (5분 갱신)
        ↓
JSON / CSV / Parquet
        ↓
Python → 새 ID 확인 → SQLite
```

| 장점 | 단점 |
| --- | --- |
| HTML 파싱 없음 — DOM 변경에 깨지지 않는다 | 제공 형식·필드·URL 안정성을 직접 확인해야 한다 |
| 이미 구조화된 데이터 (id, 시각, 본문) | 서드파티 의존 — 중단 시 대안 필요 |
| Parquet 제공 — 현재 저장 방식과 바로 맞물린다 | |
| 과거 이력 포함 — 백필이 가능하다 | **얼마나 과거까지 있는지 확인 필요.** 90D 변화율에는 180일치가 필요하다 (7절) |

**첫 작업은 이 archive의 실제 파일 URL·스키마·갱신 주기·이력 범위를 확인하는 것이다.** 이게 확인되면
`Trump's Truth` HTML 파싱은 백업 경로로만 남긴다.

### 2순위 — Trump's Truth (HTML)

페이지에는 게시물마다 다음 정보가 노출된다. ([Trump's Truth][1])

```
Donald J. Trump
@realDonaldTrump
September 13, 2026, 8:50 PM

Congratulations to Shane Lowry...
```

탐색용 최소 코드:

```python
import requests
from bs4 import BeautifulSoup

url = "https://www.trumpstruth.org/"
response = requests.get(url, headers={"User-Agent": "Mozilla/5.0"})
soup = BeautifulSoup(response.text, "html.parser")
print(soup.get_text("\n", strip=True))
```

**이 코드를 그대로 운영용으로 만들지 않는다.** 실제 HTML에서 게시물 하나가 어떤 DOM 구조인지 —
고유 ID가 어디에 있는지, 원문 링크가 있는지, 시각의 타임존은 무엇인지 — 먼저 확인한 뒤 파서를 짠다.

## 2. 수집 — 새 게시물만 가져온다

핵심은 **중복 제거**다. 매일 전체를 다시 저장하거나 분석하지 않는다.

```
오늘 archive의 최근 게시물 N개
            ↓
   DB에 이미 존재하는 id?
      ↓            ↓
     YES           NO
      ↓            ↓
     무시          저장 → 분석 대기열
```

게시물 하나는 다음 형태로 정규화한다.

```json
{
  "id": "unique-post-id",
  "published_at": "2026-09-14T00:50:00Z",
  "author": "Donald J. Trump",
  "username": "realDonaldTrump",
  "content": "Congratulations to Shane Lowry...",
  "source": "cnn-archive",
  "source_url": "...",
  "collected_at": "2026-09-13T23:00:00Z"
}
```

| 필드 | 주의점 |
| --- | --- |
| `id` | 가장 중요. archive가 주는 원본 ID를 그대로 쓴다. 없으면 `published_at + content` 해시로 대체 |
| `published_at` | **내부 저장은 전부 UTC.** 8절의 가격 결합에서 봉과 정렬해야 한다. KST·ET 변환은 표시할 때만 |
| `content` | 원문 그대로. ReTruth(재게시)·이미지만 있는 글·링크만 있는 글도 빈 문자열이 아닌 표시로 구분 |
| `source` | 어느 경로로 왔는지. 두 소스를 병행할 때 출처를 잃지 않기 위해 |

## 3. 저장 — SQLite와 Parquet

지금 규모에서는 PostgreSQL이 필요 없다. **SQLite 하나**로 시작한다.

```
data/
├── raw/
│   └── trump/
│       ├── posts/2026-09-14.parquet        ← 그날 수집한 게시물 원본 (재처리용)
│       └── bars/SPY/2026-09-14.parquet     ← 관찰 자산 분봉 (9절 — 확보 경로에 따라 5분봉 또는 1분봉)
│
└── database/
    └── trump.db                            ← 정본. 게시물 + 분류 + 이벤트 + 반응
```

### 테이블 — `trump_posts` (게시물 하나 = 행 하나)

| 컬럼 | 채우는 쪽 | 설명 |
| --- | --- | --- |
| `id` | 수집 | PK. 원본 게시물 ID |
| `published_at` | 수집 | 게시 시각 (UTC) |
| `content` | 수집 | 본문 |
| `source` / `source_url` | 수집 | 출처 · 원문 링크 |
| `collected_at` | 수집 | 수집 시각 (UTC) |
| `noise_reason` | 사전 필터 | `no_text` / `bare_reshare` / `greeting` / `too_short` / NULL. 5절 |
| `ai_topic` | Gemini | 시장 주제 또는 비시장 버킷. 4-A |
| `ai_subtopic` | Gemini | Tariff · Rate Cut … |
| `ai_target_country` | Gemini | JSON 배열 |
| `ai_target_sector` | Gemini | JSON 배열 (고정 목록) |
| `ai_mentioned_companies` | Gemini | **본문에 실제로 언급된** 티커만 |
| `ai_direction` | Gemini | positive / negative / neutral |
| `ai_intensity` | Gemini | 1–10. **정책 구체성 척도** — 4-A의 기준표 |
| `ai_market_relevance` | Gemini | 0–3. 시장과의 직접 연결 정도. 5절 |
| `event_id` | 파이썬 | 6절 클러스터링 결과. FK → `trump_events` |
| `analyzed_at` | 분류 | NULL이면 분류 대기 |

`ai_market_impact`는 **두지 않는다.** 시장 영향은 8절에서 가격으로 계산한다. 감정의 강도와 시장 영향력은 다른 것이다.

### 테이블 — `trump_events` (이벤트 하나 = 행 하나)

| 컬럼 | 설명 |
| --- | --- |
| `event_id` | PK. 예: `evt_20260915_trade_china_01` |
| `topic` / `subtopic` / `target` | 클러스터 기준값 |
| `first_post_at` | 첫 게시물 시각 (UTC). **이벤트 스터디의 기준 시각** |
| `last_post_at` / `post_count` | 마지막 게시물 · 묶인 게시물 수 (연타 자체가 신호) |
| `event_direction` | **intensity 가중 다수결.** 동률이면 neutral. 첫 게시물 값을 그대로 쓰지 않는다. 6절 |
| `event_intensity` | 묶인 게시물의 **최대값.** 반복 가산은 하지 않는다 (post_count와 이중 계산) |
| `mapping_rule_id` | 4-B 매핑 규칙 ID. 리포트가 "왜 이 종목인가"를 이 규칙에서 읽어 설명한다 |
| `affected_companies` | 규칙이 산출한 티커 배열 + 언급된 기업 |
| `market_session` | `regular` / `pre` / `after` / `closed`. 장외면 다음 개장이 기준점 |
| `confounded_intraday` | 첫 게시물 ±30분 안에 거시 발표·관찰 종목 실적이 있으면 true. 8절 |
| `confounded_daily` | 같은 거래일에 거시 발표·관찰 종목 실적이 있으면 true. 8절 |

### 테이블 — `event_reactions` (이벤트 × 자산 = 행 하나)

| 컬럼 | 설명 |
| --- | --- |
| `event_id` / `symbol` | FK · 자산 |
| `baseline_price` | 기준 시각 **직전** 봉의 종가 (장외면 다음 개장 첫 봉 시가) |
| `ret_close` / `ret_next_close` | **MVP 구간.** 당일 종가 · 익일 종가 수익률 |
| `ret_5m` / `ret_15m` / `ret_60m` | 분봉 확보 후 채운다. 없으면 NULL |
| `abn_*` | 같은 구간의 SPY 수익률을 뺀 **초과 반응.** SPY 행은 NULL |

### 테이블 — `mapping_rules` (정적, 코드와 함께 버전 관리)

| 컬럼 | 설명 |
| --- | --- |
| `rule_id` | PK. 예: `trade_china_semis` |
| `match_topic` / `match_target` | 적용 조건 |
| `sector` / `etf` | Semiconductor / SMH |
| `companies` | ETF 상위 10종목 (수동 갱신) |
| `path_text` | "China → Import Tariff → Semiconductor". 리포트 설명용 |

분류 컬럼이 NULL인 행만 골라 Gemini에 보내면 "새 게시물만 분석"이 자연스럽게 된다.
Parquet 원본은 분류 기준을 바꿔 **전체 재분석**할 때를 위한 보험이다.

## 4. 분류 — Gemini가 라벨을 붙이고, 파이썬이 나머지를 한다

### 4-A. Gemini — 게시물 하나를 구조화한다

Gemini의 역할은 **문장을 라벨로 바꾸는 것**까지다. 트렌드 판단도, 시장 영향 판단도 하지 않는다.

Trump가 중국 관세 관련 글을 올렸다면:

```json
{
  "post_id": "123456",
  "topic": "Trade",
  "subtopic": "Tariff",
  "target_country": ["China"],
  "target_sector": ["Semiconductor", "Consumer Electronics"],
  "mentioned_companies": ["NVDA", "AAPL"],
  "direction": "negative",
  "intensity": 8,
  "market_relevance": 3
}
```

**topic은 고정 목록(enum)** 이다. 시장 주제만 주면 모델이 골프 글을 억지로 "Trade"에 끼워 넣는다.
비시장 버킷을 **명시적으로** 줘야 한다.

```
시장 관련:  Trade · Fed · Tax · Energy · Immigration · Regulation · Geopolitics · Company
비시장:     Personal · Sports · Media/Press · Campaign/Politics · Legal · Congratulations · Other
```

**intensity 1–10은 기준표 없이 쓰면 안 된다.** 오늘 8, 내일 6이 나와 30일 뒤 데이터가 흔들린다.
아래 기준표는 감정의 세기가 아니라 **정책 구체성**을 재는 척도다. 컬럼 이름을 `intensity`로 두더라도 프롬프트에 이 정의를 고정한다.

| 점수 | 기준 | 예 |
| --- | --- | --- |
| 1–2 | 단순 언급 | "중국이 또 그런다" |
| 3–4 | 의견·평가 | "관세는 좋은 것이다" |
| 5–6 | 강한 주장 | "중국은 큰 대가를 치를 것" |
| 7–8 | 정책적 경고 · 구체적 조치 언급 | "반도체에 관세를 검토 중" |
| 9 | 정책 실행 예고 | "다음 주 관세를 발표할 것" |
| 10 | 즉각적 정책 발표 · 행정 조치 | "오늘 25% 관세를 부과한다" |

**출력 구조를 검증**한다 — 허용된 topic 값인지, intensity가 1–10인지, market_relevance가 0–3인지, 티커가 대문자 알파벳인지.
검증에 걸린 행은 `analyzed_at`을 비워 둔 채 다음 날 재시도한다. 기존 `validate_report.py`와 같은 방식이다.

### 4-B. 파이썬 — 언급된 기업과 영향받는 기업을 분리한다

> "China will pay a huge price for tariffs on American technology."

NVIDIA를 언급하지 않았지만 반도체 기업이 영향을 받는다. 그래서 둘을 나눈다.

| 값 | 채우는 쪽 | 기준 |
| --- | --- | --- |
| `ai_mentioned_companies` | Gemini | 본문에 **실제로 나온** 회사만 |
| `affected_companies` | 파이썬 | `mapping_rules` 테이블이 산출. **범위는 ETF 상위 10종목**까지 |

```
rule: trade_china_semis
  match:   Trade + China
  sector:  Semiconductor
  etf:     SMH
  path:    China → Import Tariff → Semiconductor
  → NVDA, AMD, AVGO, TSM, … (상위 10)
```

- 매핑을 AI에 맡기지 않는다. 정적 테이블은 결정적이고, 테스트할 수 있고, 매일 같은 답을 낸다.
- **"China + Tariff → 미국 대형 기술주 전부"** 처럼 넓게 잡지 않는다. 규칙 하나는 섹터 하나, 종목은 열 개까지다.
- 이벤트에는 적용된 `mapping_rule_id`만 남긴다. `impact_path`를 자유 텍스트로 이벤트마다 쓰지 않는다 — 규칙 테이블의 `path_text`를 읽으면 된다.
- 언급된 기업은 매핑과 무관하게 **항상** `affected_companies`에 포함한다.

## 5. 노이즈 — 버리지 않고 표시한다

골프 축하, 생일 인사, 언론 비판처럼 시장과 무관한 글이 절반 가까이 될 수 있다.
이걸 **수집 단계에서 버리지 않는다.** 표시해 두고 분석 단계에서 용도별로 제외한다.

왜 버리지 않는가:

- **노이즈 자체가 신호다.** 전체 게시량, 정책 글의 비율은 "지금 무엇에 집중하고 있나"를 보여준다.
- **기준은 나중에 바뀐다.** 원본이 없으면 재분류할 수 없다.
- **경계가 흐릿하다.** "Congratulations to Shane Lowry"는 노이즈지만 "Great job, Tesla"는 아니다.
  연준 의장에 대한 인신공격은 개인 감정 글처럼 보이지만 금리 신호다. 키워드로 미리 자르면 이런 걸 놓친다.

### 3단계 필터

**1단계 — 결정적 사전 필터 (파이썬, 무료).** 확실한 것만 걸러 Gemini 호출을 줄인다. 애매하면 통과시킨다.

| 조건 | `noise_reason` |
| --- | --- |
| 본문 없음 (이미지·영상·링크만) | `no_text` |
| 코멘트 없는 단순 ReTruth | `bare_reshare` |
| Congratulations / Happy Birthday / RIP 등으로 시작하는 짧은 글 | `greeting` |
| 단어 몇 개짜리 글 | `too_short` |

**2단계 — Gemini 분류에 비시장 버킷 + `market_relevance`.** 4-A의 enum과 함께 0–3 척도를 받는다. 기준표는 프롬프트에 고정한다.

| 값 | 의미 | 예 |
| --- | --- | --- |
| 0 | 시장과 무관 | 골프, 생일 축하 |
| 1 | 간접적인 경제·정책 관련 | 선거 유세, 언론 비판, 일반적 경제 자랑 |
| 2 | 특정 산업·자산에 직접 영향 가능, 대상 불특정 | "관세는 좋은 것이다", "금리가 너무 높다" |
| 3 | 관세·금리·제재·규제·기업 등 **즉각적 시장 영향 가능**, 대상 지정 | "중국 반도체에 관세 부과 검토", "파월은 즉시 인하해야" |

**3단계 — 분석 용도별 임계값.** 노이즈를 어디까지 쓸지 단계마다 다르게 정한다.

| 용도 | 포함 기준 |
| --- | --- |
| 게시량 · 정책 글 비율 | 전체 (노이즈 포함) |
| 3D/7D/30D/90D 주제 트렌드 | `market_relevance ≥ 1` |
| 이벤트 클러스터링 · 이벤트 스터디 | `market_relevance ≥ 2` |

### 주의

- **놓치는 쪽이 더 비싸다.** 노이즈를 잘못 넣으면 통계가 조금 흐려지지만, 관련 글을 버리면 이벤트가 사라진다.
  필터는 포함 쪽으로 기울인다. 남은 잡음은 이벤트 스터디의 표본 조건과 초과 반응이 흡수한다.
- **검증한다.** 백필한 30일치에서 50개를 무작위로 뽑아 직접 라벨을 달고 Gemini 결과와 비교한다.
  노이즈 비율과 틀리는 방향을 보고 임계값을 조정한다. 13절 ④의 완료 기준이다.
- **키워드만으로 결정하지 않는다.** "China"가 없는 관세 글, 회사명이 없는 규제 글을 놓친다.
- **감성분석 모델을 따로 두지 않는다.** Gemini 분류 하나로 충분하고, 별도 모델은 유지 비용만 늘린다.

## 6. 이벤트 — 게시물 1개 ≠ 이벤트 1개

Trump는 같은 주제로 연달아 글을 올린다.

```
10:01  Tariff / China
10:04  Tariff / China
10:07  Tariff / China
10:12  Tariff / China
10:20  Tariff / China
```

게시물마다 가격 반응을 재면 **하나의 사건을 다섯 개의 독립 표본으로 착각**한다. 통계가 부풀고 신뢰구간이 거짓으로 좁아진다.

### 클러스터링 규칙 — 단순하게

```
post (market_relevance ≥ 2)
   ↓
같은 topic + subtopic + target_country(또는 target_sector)
   ↓
직전 게시물과 60분 이내
   ↓
같은 event_id
```

- 이벤트 시각 = **첫 게시물** 시각. 이벤트 스터디의 기준점이다.
- 60분 간격, 주제 일치 기준은 처음엔 고정값으로 두고 백필 데이터를 보며 조정한다.
- 복잡한 클러스터링(임베딩 유사도 등)은 지금 단계에서 하지 않는다.

### 이벤트의 방향과 강도 — 파이썬이 다시 계산한다

```
post 1  negative  8
post 2  negative  6
post 3  neutral   3
post 4  negative  7
```

첫 게시물 값을 그대로 가져오면 안 된다.

| 값 | 계산 | 이유 |
| --- | --- | --- |
| `event_direction` | **intensity 가중 다수결.** 위 예에서 negative 21 vs neutral 3 → negative. 동률이면 neutral | 범주형을 평균하면 안 된다 |
| `event_intensity` | **최대값.** 위 예에서 8 | "가중평균 + 반복 가산"은 쓰지 않는다. 반복은 이미 `post_count`와 Trend Score의 빈도 성분에 들어 있어 세 번 계산된다 |
| `post_count` | 묶인 게시물 수 | **연타 자체가 강도 신호**이므로 버리지 않는다 |

시장 반응 통계는 **전부 이벤트 단위**로 계산한다. 게시물 단위 통계는 만들지 않는다.

## 7. 트렌드 — 네 개의 창과 Trend Score

### 네 개의 창 — 같은 길이끼리 비교한다

| 창 | 역할 | 비교 대상 | 주의 |
| --- | --- | --- | --- |
| 3D | 최근 급변 | **직전 3D** | 게시물 수가 적어 잡음이 크다. N을 함께 표시 |
| 7D | 현재 이슈 | 직전 7D | 기본 창 |
| 30D | 중기 경향 | 직전 30D | |
| 90D | **90일 장기 경향** | 직전 90D | "구조적 정책 방향"이라고 쓰지 않는다 — 자주 말한 것과 정책이 지속된 것은 다르다. 지속성 지표를 따로 만든 뒤 승격 |

3D를 이전 7D와 비교하는 식으로 길이가 다른 창을 맞대면 빈도 비교가 왜곡된다. **항상 같은 길이끼리**다.

90D 변화율에는 **180일치 이력**이 필요하다. archive가 그만큼 없으면 90D는 변화율 없이 **수준값만** 보여준다.
①단계에서 이력 범위를 확인하는 이유다.

계산 항목 (전부 SQL + pandas, LLM 없음):

| 지표 | 설명 |
| --- | --- |
| 빈도 | 주제·국가·섹터·종목별 **이벤트 수** (게시물 수는 보조) |
| 평균 강도 | event_intensity 평균 · 최대 |
| 방향 편향 | negative 비율 |
| 변화 | 이번 창 vs 직전 창 — 빈도·강도가 함께 오르는지 |
| 신규 등장 | 90일 내 처음 나온 국가·기업. **별도 목록으로 보여준다** (점수에는 가산점만) |

```
최근 7일 — 이벤트 수 × 평균 강도

China         ████████   8
Tariff        █████████  9
Fed           ███        3
Oil           █████      5
NVIDIA        ██████     6
```

### Trend Score — 곱하지 말고 더한다

"급상승 트렌드" 순위를 위해 주제별 점수 하나를 만든다. **파이썬이 계산하고 Gemini는 설명만 한다.**

`빈도 변화율 × 강도 변화율 × 최근성` 같은 **곱셈 공식은 쓰지 않는다.** 세 가지가 깨진다.

| 문제 | 무슨 일이 생기나 |
| --- | --- |
| 0으로 나누기 | 직전 창에 언급이 없던 주제가 처음 등장하면 변화율이 무한대. 가장 중요한 신호에서 계산이 깨진다 |
| 부호 반전 | 빈도 감소 × 강도 감소 = 양수 → "급상승"으로 잡힌다 |
| 스케일 불일치 | 빈도는 몇 배씩 변하고 강도는 1–10 안에서만 움직여 곱하면 빈도가 점수를 독식한다 |

대신 **가중합**이다. 각 성분을 0–100으로 정규화(순위 기반)한 뒤 더한다.

```
Trend Score = 0.35 · 빈도 점수   (7D vs 직전 7D 이벤트 수 변화, 순위 정규화)
            + 0.30 · 강도 점수   (7D 평균 event_intensity)
            + 0.25 · 최근성 점수 (마지막 이벤트가 최근일수록)
            + 0.10 · 신규성 점수 (90D 내 첫 등장이면 가산)
```

**신규성은 가산점이다.** 90일 만에 처음 언급한 작은 나라가 1위로 올라오면 이상하다. 신규 등장은 위의 별도 목록에서 보여주므로 점수 비중을 낮춰도 잃는 게 없다.
가중치는 90D 백필에서 순위가 직관과 맞는지 보고 조정한다.

```
🔥 급상승 트렌드 (7D)

1. China / Tariff      87
2. Fed / Rate           74
3. Oil / Energy         61
```

## 8. 시장 반응 — 이벤트 스터디와 초과 반응

여기서부터 **Trump SNS → 시장 반응 통계 시스템**이 된다. 단순 가격 추적과의 차이는 세 가지다 — 기준가, 초과 반응, 분포 표시.

### MVP는 일 단위다

무료 플랜에서 분봉을 안정적으로 확보하기 전까지 (9절) **이벤트 스터디는 당일 종가·익일 종가로 시작한다.**

- Trump 게시물의 상당수는 장외 시간(저녁·밤·주말)에 올라온다. 이런 이벤트의 자연스러운 관측 구간은 어차피 "다음 개장 → 종가"다.
- 이 프로젝트의 질문은 "발언 후 며칠간 어떤 반응이 반복됐나"다. 분 단위는 정규장 게시물에 대한 **추가 해상도**이지 전제가 아니다.
- 일 단위는 기존 `collect_yahoo.py`가 이미 받는다. 새 코드가 거의 없다.

분 단위 구간(+5m/+15m/+60m)은 스키마에 자리를 비워 두고, 분봉이 확보되는 시점부터 채운다.

### 기준가 — 게시 직전 가격을 반드시 저장한다

```
이벤트 첫 게시물   09:32:17 ET
      ↓
baseline           09:32 이전 마지막 봉의 종가 (일 단위면 전일 종가)
      ↓
+5m / +15m / +60m  (분봉 확보 후)
당일 종가 · 익일 종가 (MVP)
```

- 게시물과 봉의 timestamp는 **모두 UTC**로 맞춘 뒤 비교한다. 여기서 타임존이 어긋나면 모든 통계가 틀린다.
- 장외 게시물은 **다음 개장 첫 봉 시가**를 기준가로 삼고 `market_session`에 표시한다. 주말·휴장도 같다.

| 구간 | 용도 | 단계 |
| --- | --- | --- |
| 당일 종가 | 하루 반응 | **MVP** |
| 익일 종가 | 장외·주말 게시물 포함 전체 | **MVP** |
| +5분 / +15분 / +60분 | 즉각 반응 (정규장 게시물만) | 분봉 확보 후 |

### 초과 반응 — 시장 전체 움직임을 뺀다

그날 시장이 전부 내렸으면 Trump 때문인지 알 수 없다.

```
NVDA 실제 수익률   -2.1%
SPY  수익률        -0.8%
──────────────────────────
초과 반응          -1.3%
```

MVP는 **단순 시장조정**(자산 수익률 − SPY 수익률)이다. NVDA가 평소 SPY의 두 배로 움직이는 종목이라는 사실은 반영하지 않는다.
이건 알고 있는 한계다. 표본이 쌓이면 **기대수익률 모형**(SPY·QQQ·섹터 ETF를 설명변수로 한 회귀)으로 바꾼다. **지금은 하지 않는다.**
SPY 자체는 벤치마크가 없으므로 원수익률만 기록한다.

### 혼재 이벤트 — 구간별로 두 개의 플래그

FOMC, CPI, 고용지표, 대형 실적 발표가 관측 구간에 겹치면 초과 반응을 계산해도 오염된다.
창을 하나로 고정하지 않는다 — **분 단위와 일 단위의 오염 조건이 다르다.**

| 플래그 | 조건 | 적용 구간 |
| --- | --- | --- |
| `confounded_intraday` | 첫 게시물 **±30분** 안에 아래 이벤트 | +5m / +15m / +60m |
| `confounded_daily` | **같은 거래일**(장외면 다음 거래일)에 아래 이벤트 | 당일 종가 / 익일 종가 |

판정 대상 이벤트:

| 종류 | 소스 |
| --- | --- |
| FOMC 결정 · 의사록 | FRED 릴리스 캘린더 |
| CPI · PCE · 고용(NFP) · GDP | FRED 릴리스 캘린더 |
| 관찰 종목 실적 발표 | 관찰 종목(15개 이내)의 발표일만 확인 |
| 거래 정지 · 조기 폐장 | 거래소 캘린더 |

통계에서는 `confounded = false`인 **clean 이벤트만** 기본으로 쓰고, 전체와 confounded 수를 함께 표시한다.

```
Tariff 이벤트   전체 N = 43   clean N = 31   confounded N = 12
```

### 통계 — 평균 하나로 끝내지 않는다

`N = 50, 평균 -0.8%`는 표준편차가 5%일 때와 0.7%일 때 완전히 다른 결과다.
주제 × 자산 × 구간마다 다음을 저장하고 리포트에도 이 형태로 낸다.

| 항목 | 이유 |
| --- | --- |
| N (clean 이벤트 수) | 20개 미만이면 리포트에 내지 않는다 |
| Mean | |
| Median | 수익률은 꼬리가 두꺼워 평균이 몇 개 이상치에 끌려간다 |
| Std | |
| Positive % / Negative % | 승률. 방향의 일관성을 가장 직관적으로 보여준다 |
| (나중에) 신뢰구간 | 부트스트랩으로. 표본이 충분해진 뒤 |

```
Trump의 Tariff 이벤트 — clean 31건 · 초과 반응 · 당일 종가

        Mean     Median   Std     Neg%
QQQ    -0.21%   -0.15%   0.9%    62%
SMH    -0.71%   -0.55%   1.4%    70%
NVDA   -1.02%   -0.80%   2.1%    68%
```

### 표현 — 인과를 단정하지 않는다

"Trump 발언 때문에 SMH가 -2% 하락했다"고 쓰지 않는다. 같은 시간에 Fed, 중국 PMI, 실적, 금리, 유가가 움직였을 수 있다.
Gemini 프롬프트에 문구 규칙을 고정한다.

| 쓰지 않는다 | 쓴다 |
| --- | --- |
| "영향을 미쳤다" · "하락시켰다" | "발언 이후 다음과 같은 반응이 **관찰됐다**" |
| "때문에" | "과거 유사 발언 N건 이후 평균적으로" |

AlphaFlow의 투자 판단 시스템과 연결할 때 이 구분이 특히 중요하다.

## 9. 가격 데이터 — 무료 플랜에서 어디까지 되나

결론부터: **리포트는 무료 플랜으로 구현 가능하다.** 분 단위 해상도만 경로에 따라 제약이 있고, MVP는 그것 없이 성립한다.

### 서비스별 점검

| 구간 | 서비스 | 비용 | 제약 | 판단 |
| --- | --- | --- | --- | --- |
| 게시물 | CNN archive (공개 파일) | 무료, 키 없음 | 이력 범위 확인 필요 | 문제 없음 |
| 게시물 백업 | Trump's Truth (HTML) | 무료 | 하루 1회 요청 수준 | 문제 없음 |
| 일봉 | yfinance (기존 `collect_yahoo.py`) | 무료, 키 없음 | 비공식 라이브러리. 간헐적으로 깨진다 | **MVP 충분.** 이미 운영 중 |
| 분봉 | yfinance 5분봉 | 무료, 키 없음 | 조회 가능 기간 약 60일. 백필 불가 | ETF 위주 소수 종목에 쓸 수 있다 |
| 분봉 | yfinance 1분봉 | 무료, 키 없음 | 요청당 7일, 조회 가능 기간 약 30일. 가장 자주 깨지는 구간 | **의존하지 않는다** |
| 분봉 | 무료 API (Polygon Basic · Alpaca IEX 등) | 무료 키 1개 | 분당 요청 제한, 지연 데이터. **과거 분봉 백필이 가능한 곳이 있다** | 확인 후 채택 — 백필이 되면 "지금 시작해야 한다"는 압박이 사라진다 |
| 분류·서술 | Gemini (무료 등급) | 무료 | 분당·일일 요청 수. 12절 | 배치로 충분 |
| 실행 | GitHub Actions | 공개 저장소 무료 | 실행 시간 한도 | 기존 파이프라인과 동일 |
| 게시 | Blogger API | 무료 | | 기존과 동일 |

한도 숫자는 문서에 박지 않는다. 각 서비스의 현재 값을 ①단계에서 확인하고 코드의 설정값으로 둔다.

### 1분봉에 대한 판단 — 필수가 아니다

이전 개정에서 "1분봉은 지나가면 받을 수 없으니 지금 시작해야 한다"고 썼다. 그 전제를 다시 본다.

- **yfinance 기준으로는 맞다.** 1분봉은 최근 약 한 달치만 조회되고 그 뒤로는 사라진다.
- **하지만 분 단위 이력을 제공하는 무료 API가 있다.** 무료 키 하나로 수년치 분봉을 뒤에서 받을 수 있는 서비스가 있다면, 지금 매일 쌓지 않아도 나중에 이벤트 날짜만 골라 백필할 수 있다. 이게 확인되면 분봉 수집은 "지금 당장"에서 "필요할 때"로 내려간다.
- **분 단위가 없어도 리포트의 질문에 답할 수 있다.** 8절에 쓴 대로 장외 게시물이 많고, 핵심 통계는 종가 기준이다.

그래서 분봉의 우선순위를 이렇게 정한다.

| 단계 | 할 일 |
| --- | --- |
| 지금 | **일봉으로 MVP.** 기존 수집기에 관찰 종목 몇 개만 추가 |
| ①단계에서 함께 | 무료 API 하나 계정 생성 → 분봉 이력 범위·요청 한도 확인 |
| 백필 가능하면 | 분봉 수집을 서두르지 않는다. ⑥에서 이벤트 날짜만 골라 받는다 |
| 백필 불가능하면 | yfinance **5분봉**을 ETF 7개 + 언급 종목 소수에 대해 매일 쌓는다. 1분봉은 포기 |

5분봉이면 +5m는 "첫 5분봉", +15m·+60m는 그대로 계산할 수 있다. 1분봉과의 차이는 이 프로젝트의 질문에 영향을 주지 않는다.

### 관찰 종목 — 처음부터 많이 잡지 않는다

이 프로젝트의 핵심은 **개별 종목 예측이 아니라 발언의 시장·산업 반응 패턴**이다.

| 그룹 | 종목 | 이유 |
| --- | --- | --- |
| 시장 | SPY · QQQ | 벤치마크 · 성장주 |
| 섹터 ETF | SMH · XLK · XLF · XLE · XLV · XLI | Trump 주제와 맞닿는 섹터. 기존 수집기에 대부분 있다 |
| 직접 언급 종목 | NVDA · TSLA · AAPL 등 **Trump가 이름을 부르는 회사** 5개 이내 | `ai_mentioned_companies` 상위에서 고른다 |

합쳐서 **15개 이내.** 수백 종목 분봉은 관리 비용만 늘리고 통계에는 기여하지 않는다.
`affected_companies`의 나머지 종목은 일봉으로만 본다 — 일봉은 유니버스가 커도 부담이 없다.

기존 데일리 리포트의 한 섹션으로 들어가거나, 별도 글로 나간다. 표는 파이썬이 그리고 문장은 Gemini가 쓴다.

Gemini에게 주는 것은 7·8절의 **집계 결과 JSON**이지 원문 게시물 전체가 아니다.

## 11. 자동 실행

| 단계 | 방법 | 이유 |
| --- | --- | --- |
| 개발 초기 | **Windows 작업 스케줄러** — 매일 08:00 KST | 가장 빠르게 돌려 볼 수 있다 |
| 안정화 후 | GitHub Actions cron | 기존 데일리 리포트와 같은 자리에서 관리 |

```
매일 08:00 KST
    ↓
collect_trump.py    — archive 확인 → 새 게시물 저장 → 사전 필터
collect_bars.py     — (분봉 경로가 정해진 뒤) 관찰 종목 15개 이내 분봉 누적
    ↓
classify_trump.py   — analyzed_at IS NULL → 배치로 Gemini → 항목별 검증 → 저장
    ↓
cluster_events.py   — event_id · event_direction/intensity · mapping_rule_id · market_session · confounded_*
    ↓
aggregate_trump.py  — 3D/7D/30D/90D 집계 · Trend Score · 이벤트 반응 · 통계
    ↓
(기존 데일리 리포트 파이프라인에 JSON 전달)
```

SQLite 파일을 GitHub Actions에서 쓰려면 기존 `report-state` 브랜치처럼 **상태를 브랜치에 커밋**하거나,
DB를 Parquet로 내보내 저장해야 한다. Actions로 옮길 때 결정한다.

## 12. Gemini 호출 유의점 — 여러 키와 배치

### 지금 코드가 하는 것

[`generate_report.py`](../experiments/daily-report/generate_report.py)는 `GEMINI_API_KEY`를 세미콜론이나 쉼표로 나눠
여러 키를 받는다. 방식은 **장애 대비 순차 전환**이다 — 1번 키로 정해진 횟수만큼 시도하고 실패하면 2번 키로.
하루 한 번 큰 호출을 하는 데일리 리포트에는 이걸로 충분하다.

### 트럼프 파이프라인은 호출 패턴이 다르다

| 구분 | 데일리 리포트 | 트럼프 분류 |
| --- | --- | --- |
| 호출 수 | 하루 1회 | 하루 수십 게시물 + 백필 수천 건 |
| 호출 크기 | 큼 (수집 전체) | 작음 (게시물 하나) |
| 실패 비용 | 리포트 미게시 | 해당 게시물만 다음 날 재시도 |

### 키를 늘리기 전에 — 배치가 먼저다

게시물 10~20개를 한 번에 보내 **JSON 배열**로 받으면 호출 수가 10분의 1로 줄어든다.
5절 1단계 사전 필터로 노이즈를 먼저 빼면 더 줄어든다. 이렇게 하면 **일일 운영은 키 하나로도 무료 한도 안에 든다.**

여러 키가 실제로 필요한 곳은 두 군데다.

| 상황 | 대응 |
| --- | --- |
| 초기 백필 (30~90일치) | 분당·일일 한도에 걸린다. 키를 나누거나 **호출 사이에 대기를 두고 이틀에 나눠** 돌린다 |
| 장애 대비 | 한 키가 429·일시 오류를 내면 다음 키로. 지금 코드가 이미 하는 일 |

### 코드에서 바꿀 것

기존 키 표기 방식(`;` 구분)은 그대로 두고 호출 쪽만 보강한다.

- **순차 전환 → 라운드로빈.** 호출마다 다음 키를 쓰고, 429를 받은 키는 일정 시간 쉬게 표시한다. `_api_keys()`는 그대로 재사용.
- **배치 단위가 아니라 항목 단위로 검증.** 배열 응답에서 항목별로 구조 검증을 하고 통과한 것만 DB에 쓴다. 하나가 깨져도 배치 전체를 버리지 않는다.
- **중복 안전.** 키를 바꿔 재시도하다 같은 게시물을 두 번 분류해도 `analyzed_at IS NULL`인 행만 갱신하므로 문제없다.
- **모델 고정.** 모든 키가 같은 `GEMINI_MODEL`을 쓴다. 키마다 모델 버전이 다르면 라벨 일관성이 깨져 트렌드 비교가 무의미해진다.
- **배치 크기는 10~20.** 너무 크면 응답 JSON이 깨지는 빈도가 올라간다.

### 주의

- **한도는 프로젝트 단위다.** Google Cloud 프로젝트를 나눠 키를 만들면 한도가 각각 적용되는 것이 공식 동작이다.
  다만 **여러 계정을 만들어 한도를 우회하는 것은 약관 위반**이다. 같은 계정 안의 프로젝트 분리까지만 쓴다.
- **정확한 한도 숫자는 확인이 필요하다.** 무료 등급의 분당·일일 요청 수는 모델과 시기에 따라 바뀌어 왔다.
  AI Studio의 현재 값을 보고 배치 크기와 대기 시간을 정한다. 이 문서에 숫자를 박아 두지 않는다.
- **백필은 서두를 이유가 없다.** 게시물 분류는 나중에 해도 결과가 같다.
  키를 늘리는 대신 대기를 두고 나눠 돌리는 쪽이 단순하다.
- **비용은 문제가 안 된다.** 하루 게시물이 수십 개 수준이고 사전 필터가 절반 가까이 줄인다. Flash급으로 전량 분류해도 부담이 없다.

## 13. 도입 순서

기존 파이프라인처럼 **그림자 모드**부터. 리포트에 실리기 전까지는 어디에도 게시하지 않는다.

| 단계 | 할 일 | 완료 기준 |
| --- | --- | --- |
| ① 소스·한도 확인 | CNN archive의 URL·스키마·갱신 주기·**이력 범위** 확인. 무료 분봉 API 1개 계정 생성 → 백필 가능 여부·요청 한도 확인. Gemini 무료 한도 확인 | 최근 게시물 10개를 JSON으로 손에 든다. 분봉 경로가 "백필 가능 / 5분봉 매일 / 없음" 중 하나로 결정된다 |
| ② 수집 + 사전 필터 | `collect_trump.py` — 새 게시물만 SQLite 저장 + 일별 Parquet + `noise_reason` | 이틀 연속 돌려 중복 0건 |
| ③ 가격 준비 | 기존 `collect_yahoo.py` 유니버스에 관찰 종목 추가 (일봉). 분봉은 ①의 결정에 따라 — 백필 불가면 5분봉 누적 시작 | 관찰 종목 15개 이내의 일봉이 매일 갱신된다 |
| ④ 스키마 확정 + 분류 | 3절 네 테이블 + `mapping_rules` 초안 확정 → `classify_trump.py` — 배치 Gemini + 항목별 검증 | 30일치 백필, 검증 실패율 < 5%, **50개 수동 라벨 대비 노이즈 판정 일치 확인** |
| ⑤ 이벤트 + 집계 | `cluster_events.py` · `aggregate_trump.py` — event_id, 방향·강도 재계산, 네 개 창(같은 길이), Trend Score(가중합) | 급상승 표가 그려지고 순위가 직관과 맞는다 |
| ⑥ 시장 결합 | 이벤트 스터디 — **당일·익일 종가 먼저.** 기준가·초과 반응·confounded 두 플래그. 분봉은 경로가 있으면 이벤트 날짜만 백필 | 주제 × 자산 표 하나 이상 clean N ≥ 20 도달 |
| ⑦ 리포트 | 기존 데일리 리포트에 섹션 추가 또는 별도 글. "관찰됐다" 어법 | 그림자 모드 2주 후 게시 |

순서에 대해 두 가지를 못 박아 둔다.

- **①②③은 지금 바로 시작한다.** 분석 설계를 다듬는 동안에도 수집은 돌고 있어야 한다.
- **스키마(event_id · mapping_rule_id · 기준가 컬럼 · confounded 두 개)는 ④ 전에 확정한다.** 분류는 백필할 수 있지만 스키마를 나중에 바꾸면 전부 다시 돈다.

나머지 세부값(클러스터 간격, 가중치, 임계값)은 **실제 데이터를 2주 쌓으면서 고친다.** 기획을 완벽하게 만든 뒤 시작하지 않는다.

지금 만들지 않는 것: 별도 감성분석·ML 모델, 임베딩 클러스터링, 실시간 스트리밍, 기대수익률 모형(팩터 조정), 1분봉 대규모 유니버스.

## 14. 기존 파이프라인과의 관계

| 재사용 | 새로 만드는 것 |
| --- | --- |
| Gemini 호출·다중 키·재시도 패턴 (`generate_report.py`) | 게시물 수집기 + 사전 필터 |
| 구조 검증 방식 (`validate_report.py`) | SQLite 스키마 네 테이블·중복 제거 |
| 가격 수집 (`collect_yahoo.py`) — 일봉 유니버스에 종목 추가 | 분봉 수집 (경로 결정 후) |
| HTML 렌더·게시 (`render_html.py`, `publish_blogger.py`) | 이벤트 클러스터링 · 이벤트 스터디 · 초과 반응 |
| `report-state` 브랜치 이력 저장 | 분류 enum · intensity/relevance 기준표 · 프롬프트 · `mapping_rules` · 경제 캘린더 |

설계 원칙은 같다. **숫자는 파이썬이 계산하고 Gemini는 문장만 쓴다.** 이 프로젝트에서 Gemini의 자리는 딱 둘이다 —
게시물에 라벨을 붙이는 **입력**과 집계 결과를 문장으로 옮기는 **출력**. 시장 영향·트렌드·인과는 전부 파이썬 쪽에 있다.

## 개발 전 확정값

| 항목 | 확정 |
| --- | --- |
| 이벤트 방향 | intensity 가중 다수결. 동률이면 neutral |
| 이벤트 강도 | 게시물 최대값. 반복 가산 없음 |
| confounded | `intraday`: 첫 게시물 ±30분 내 FOMC·CPI·PCE·NFP·GDP·관찰 종목 실적. `daily`: 같은 거래일에 위 이벤트 |
| Trend Score 가중치 | 빈도 0.35 · 강도 0.30 · 최근성 0.25 · 신규성 0.10 |
| 비교 구간 | 같은 길이끼리 — 3D/3D · 7D/7D · 30D/30D · 90D/90D. 직전 구간이 없으면 수준값만 |
| 매핑 범위 | `mapping_rules` 정적 테이블. 규칙 하나 = 섹터 하나 = ETF 상위 10종목. 언급된 기업은 항상 포함 |
| 관찰 종목 | 15개 이내 — SPY·QQQ + 섹터 ETF 6 + 직접 언급 종목 ≤ 5 |
| 이벤트 스터디 MVP 구간 | 당일 종가 · 익일 종가. 분 단위는 분봉 경로 확보 후 |

## 열린 질문

- **CNN archive 접근성과 이력 범위** — URL·스키마·얼마나 과거까지 있는지. 180일 미만이면 90D는 수준값만.
- **분봉 경로** — 무료 API 중 분봉 백필이 되는 곳이 실제로 있는지, 요청 한도가 15종목 × 이벤트 날짜 조회에 충분한지. ①에서 결정.
- **분류 enum 초안** — 시장 8개 + 비시장 7개로 시작하고 데이터를 보고 쪼갠다.
- **클러스터링 파라미터** — 60분 간격, 주제 일치 기준이 실제 연타 패턴과 맞는지 백필로 확인.
- **Trend Score 가중치** — 0.35/0.30/0.25/0.10 시작. 백필 순위가 직관과 맞는지로 조정.
- **`mapping_rules` 초안** — 규칙 몇 개로 시작할지 (Trade×China, Fed×Rate, Energy×Oil, Company×직접 언급 정도). ETF 구성종목 갱신 주기.
- **경제 캘린더 소스** — FRED 릴리스 캘린더로 FOMC·CPI·PCE·NFP·GDP가 충분한지. 실적 발표일은 어디서 받을지.
- **저장 위치** — GitHub Actions로 옮길 때 SQLite 브랜치 커밋 vs Parquet 내보내기.
- **Gemini 무료 한도** — 현재 분당·일일 값 확인 후 배치 크기·대기 시간 결정. 12절.
- **공식 API 전환 시점** — 실시간성이 필요해지거나 아카이브가 중단되면. 비용은 그때 확인.
- **(나중에) 기대수익률 모형** — clean N이 충분히 쌓이면 SPY 단순 차감을 회귀 기반으로 교체.
