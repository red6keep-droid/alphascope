## 0. 결론

- **종목 20개를 추적하되, 글은 "움직인 종목만" 쓴다.** 매 거래일 묶음 글(종목 레이더) 1편 + 이벤트가 터진 종목만 개별 리포트(하루 최대 3편).
- 제약은 Gemini 한도가 아니라 **블로그 글 수(스팸 판정)와 사람이 검토할 수 있는 양**이다. 하루 20편은 둘 다 넘는다.
- Gemini는 분류를 flash-lite, 서술만 3.5-flash 로 하면 20개 종목도 **무료 프로젝트 2~3개** 안에 든다. 유료는 종목 수가 아니라 "무료 프로젝트 여러 개를 한 계정에서 돌리는 약관 위험"을 없애고 싶을 때의 선택이다.
- 종목을 늘리는 단위는 종목이 아니라 **섹터 템플릿**(이벤트 정의 · 전용 소스 · 관련 티커). 템플릿 없이 종목만 늘리면 밋밋한 글이 된다.
- 순서: NVDA 그대로 유지(검증된 템플릿 · 카나리아) → 반도체 템플릿으로 3~4종목 레이더 → 섹터 템플릿 추가 → 20개.

## 1. 왜 "종목마다 매일 한 편"이 안 되나

| 제약 | 내용 | 수치 |
|---|---|---|
| Gemini 3.5-flash 하루 한도 | 프로젝트 × 모델당 약 20회. 503 재시도도 횟수에 든다(실측). NVDA형 리포트는 분류 2~4 + 서술 1~2 + 재분류 0~2 → **종목 1개 = 프로젝트 1개** | 키 9개 → 종목 8개가 상한 |
| flash-lite 는 버킷이 따로 | 같은 프로젝트에서 하루 500~1,000회(제3자 자료, AI Studio 에서 확인). 분류 정확도는 flash 라벨과 85% 일치(flash 자기 재현 88%) | 분류를 lite 로 돌리면 분류는 제약이 아님 |
| 블로거 스팸 판정 | 구조가 같은 자동 생성 글이 하루 20편이면 블로그 전체가 잠기거나 검색에서 내려갈 수 있다. 애드센스 자동 생성 콘텐츠 정책 | 하루 글 수를 한 자리로 |
| 검토 가능량 | 예비 · 대체 모델이 쓴 글의 방향 오류를 사람이 잡아 왔다(10-15 · 10-16). 20편은 못 본다 | 하루 5편 안팎 |
| 종목별 설계 | NVDA 이벤트 48개 → 33개 확정에 몇 주. 은행 · 제약 · 소매는 이벤트와 소스가 다르다 | 섹터 템플릿 4~5개 |
| yfinance | 비공식. 20종목 × 옵션 만기 6개면 요청 수백 회 → 러너 IP 차단 시 전부 실패 | 호출을 한 실행에서 묶고 옵션은 선별 |
| 약관 | 한 파이프라인이 무료 프로젝트 여러 개를 나눠 쓰면 "한도 우회"로 보일 수 있다(계정 단위로 막힌 사례) | 종목당 프로젝트 고정, 또는 유료 1개 |

## 2. 세 가지 방식

| 방식 | 하루 글 수 | Gemini 호출(flash / lite) | 무료로 되나 | 판정 |
|---|---|---|---|---|
| A. 종목마다 매일 1편 (지금 NVDA 방식 × 20) | 20편 + 데일리 · 트럼프 | 분류 40 + 서술 20 / 0 | 아니오 (프로젝트 12개 필요) | **스팸 · 검토 때문에 유료여도 안 됨** |
| B. 20개 추적, 이벤트 있는 날만 개별 글 | 5~8편 | 서술 5~8 / 분류 40 | 예 (2~3개) | 가능. 글이 흩어져 독자가 20개를 훑기 어렵다 |
| **C. 20개 추적, 묶음 글 1~2편 + 큰 이벤트만 개별 글** | 2~4편 | 서술 3~6 / 분류 40 | **예** | **채택** |

## 3. C 구조 — 종목 레이더

### 3-1. 독자가 보는 것

| 글 | 빈도 | 내용 |
|---|---|---|
| **종목 레이더** (묶음 글) | 매 거래일 1편 (종목이 늘면 섹터별 2편) | 추적 종목 전부를 **오늘 움직인 순**으로. 종목마다 카드 하나: 등락(섹터 ETF 대비) · 오늘 이벤트 0~3건(출처 링크) · 켜진 신호(볼린저 · 과열 · 목표가 변경 · 실적 D-n) · 한 줄 해석. 아무 일 없는 종목은 맨 아래 "조용한 종목" 한 줄 목록 |
| **개별 종목 리포트** | 조건을 만족한 종목만, 하루 최대 3편 | 지금 NVDA 리포트와 같은 전체 구조(오늘 · 캘린더 · 시장 지표 · 재무). 그 종목 라벨에 쌓인다 |
| 종목 라벨 페이지 | 항상 | 그 종목의 개별 리포트 목록. 레이더 카드로 가는 링크 |
| 홈 카드 | 매일 | 레이더에서 "오늘 움직인 종목" 상위 몇 개 |

하루 글 수 2~4편(데일리 · 트럼프 포함 4~6편). 독자는 레이더 한 편으로 전부를 훑고, 관심 종목에 일이 생긴 날만 깊은 글을 본다.

### 3-2. 개별 리포트가 나가는 조건 — 코드가 판정

- 이벤트 판정 기사(`is_event`)가 1건 이상이고 관련도 합이 기준 이상
- 또는 실적 발표일 ±1일
- 또는 가격 신호: 섹터 ETF 대비 ±2σ 이상 · 볼린저 밴드 터치 · 목표가 · 등급 변경
- 하루 3편 상한 — 점수 높은 순. 밀린 종목은 레이더 카드에 "자세한 글은 내일"
- **수동 예외**: 주인만 보는 설정 페이지(블로그 Google 로그인 재사용)에서 "꼭 올려 / 오늘은 빼"를 Firestore `publish_plan/{날짜}` 에 저장 → 워크플로가 아침에 읽어 판정을 덮어쓴다. 문서가 없으면 자동 판정. (댓글 봇의 서비스 계정 그대로)

### 3-3. 매일 도는 파이프라인 — 워크플로 1개

지금은 종목마다 워크플로 · 상태 브랜치가 따로다. C 는 **하나의 실행이 종목 전부를 차례로** 처리한다.

| 단계 | 내용 | LLM |
|---|---|---|
| 1 수집 | 시세 · 옵션 · 공시 · 뉴스를 티커 전부에 대해 한 번에. yfinance 호출은 묶고 옵션은 이벤트 후보 종목만 | — |
| 2 분류 | 기사 배치 분류 (종목당 하루 2배치 안팎) | **lite** (40회 안팎) |
| 3 판정 · 신호 | 이벤트 · 신규성 · 가격 신호 — NVDA `judge` 를 티커 · 섹터 설정으로 일반화 | — |
| 4 재확인 | **이벤트로 판정된 기사만** flash 가 다시 분류. 게시 글에 들어가는 라벨은 flash 기준 | flash 0~3회 |
| 5 선정 | 3-2 규칙으로 개별 리포트 종목 선정 | — |
| 6 서술 | 선정 종목 개별 서술(종목당 1회) + 레이더 서술(1~2회, 섹터별 또는 전체) | flash 3~6회 |
| 7 렌더 · 게시 | 레이더 1편 + 개별 0~3편. 상태 저장은 브랜치 하나 | — |

3.5-flash 하루 5~8회, lite 40회. 무료 프로젝트 2~3개. 실행 시각은 지금 NVDA 자리(뉴욕 17:30)에 두고, 개별 리포트는 레이더 뒤에 10분 간격으로 게시(분당 한도 · 카나리아).

### 3-4. 섹터 템플릿 — 종목을 늘리는 단위

종목은 `config` 의 한 줄이지만, 그 줄이 가리키는 템플릿이 있어야 한다.

| 템플릿 항목 | NVDA 에서의 예 |
|---|---|
| 이벤트 종류와 판정 기준 | 수출 규제 · HBM · 파운드리 · 소송 · 실적 가이던스 (33개) |
| 전용 소스 | NVIDIA 뉴스룸 · 연방관보(BIS) · CourtListener · TSMC 월매출 |
| 관련 티커 | 고객 · 공급 · 동종 11개, 섹터 ETF SMH |
| 재무 점검표 | 데이터센터 매출 비중 · 재고 · 가이던스 |
| 서술 지시문의 금지어 · 어법 | 공통 + 섹터 용어 |

후보 템플릿: 반도체(NVDA · AMD · AVGO · TSM …) · 소프트웨어/클라우드 · 금융 · 제약/바이오 · 소비재/소매. 템플릿 하나에 며칠, 그 안의 종목 추가는 한 시간.

### 3-5. 지금 코드와의 관계

- NVDA 리포트는 **그대로 매일 개별 리포트**로 둔다 — 검증된 템플릿이자 카나리아. 레이더에도 NVDA 카드가 들어간다.
- `experiments/nvda-report` 의 collect · classify · judge · render 를 "티커 + 템플릿" 매개변수로 일반화한 `experiments/stock-radar`(가칭)를 만든다. llm_chain · design_kit · fact_check 는 그대로.
- 레이더 글 렌더는 홈 카드와 같은 카드 묶음 + 종목 라벨 링크. 개별 리포트 렌더는 NVDA 것 재사용.

## 4. 위험과 대책

| 위험 | 대책 |
|---|---|
| 레이더 품질이 lite 분류에 좌우 | 이벤트 기사는 flash 재확인(3-3 ④). 레이더는 한 편이라 표본 검토가 쉽다 |
| 서술의 지시문 위반(예비 · 대체 모델) | 트럼프 "내일 볼 것" 검사(`check_watch`)처럼 **형식이 고정된 문장은 코드가 검증**. 레이더 한 줄 해석도 형식을 고정한다 |
| yfinance 차단 | 한 실행에서 묶어 호출 · 간격 · 옵션 선별 · 대체 소스(Stooq) |
| 공통 코드 버그가 전 종목에 동시 반영 | NVDA 먼저 게시 → 레이더 → 개별 순. 건너뛰기 조건 |
| 상태 저장 비대화 | 브랜치 하나, 주기적 압축. 커지면 Firestore/R2 |
| 분당 한도 충돌 | 한 실행이 순차 호출이라 자연히 분산. 개별 리포트 게시는 10분 간격 |
| 알림 · 댓글 폭증 | Slack 은 하루 요약 1건. 댓글 봇은 종목 묶음으로 |
| 약관 | 종목 수와 무관하게 무료 프로젝트 2~3개. 찜찜하면 유료 Tier 1 하나 |

## 5. 도입 순서

1. **반도체 템플릿 추출** — NVDA 설정에서 티커 고유값과 섹터 공통값을 분리
2. **레이더 3~4종목** (NVDA · AMD · AVGO · TSM) — 워크플로 1개, 레이더 1편, 개별 리포트는 NVDA 만. 한 달 운영: 블로거 반응 · yfinance 안정성 · lite 분류 품질
3. 개별 리포트 자동 선정(3-2) 켜기, 수동 예외 페이지
4. 섹터 템플릿 둘째 · 셋째 → 10개
5. 20개. 이때 레이더를 섹터별 2편으로 나눌지 결정

## 6. 스팸 · 검색 품질 — 글 수가 아니라 비슷함

(2026-10-16 사용자: "사람이 검수하고 독창적인 해석이면 스팸 판별에서 벗어날 수 있어?")

판별 주체는 셋이고, 보는 것이 다르다.

| 주체 | 보는 것 | 사람 검수의 효과 |
|---|---|---|
| Blogger 자동 탐지 (블로그 잠금) | 게시 속도 · API 자동 게시 패턴 · 글끼리 얼마나 비슷한가 · 링크 · 계정 이력 — 기계 신호 | 직접 효과 없음. 검수로 글이 서로 달라지는 만큼만 |
| 구글 검색 품질 (대량 생성 콘텐츠 정책, 2024~) | AI · 사람 무관. 검색 노출을 노려 대량으로 찍은 비슷한 글인가, 독자에게 고유한 가치가 있나 | 검수 자체가 아니라 "검수를 거쳐 남과 다른 해석이 들어갔는가" |
| 애드센스 | 가치를 더하지 않은 자동 생성 콘텐츠 | 위와 같음 |

- **기준은 편수가 아니라 비슷함이다.** "하루 한 자리 수"는 경험칙이지 공식 기준이 아니다(공개된 숫자 없음). 내용이 서로 다른 뉴스형 블로그는 하루 10편 넘게도 멀쩡하고, 같은 뼈대의 얇은 글은 3편도 걸린다. 편수를 줄이자는 것은 비슷함을 줄이는 가장 쉬운 방법이라서다.
- **우리 글의 강점**: 남이 못 베끼는 계산값이 매일 바뀐다 — 시장 상태 점수 · 플라시보 검정 반응 통계 · 이벤트 신규성 · 섹터 대비 등락. 얇은 AI 글이 아니라 데이터 리포트다.
- **우리 글의 약점**: ① 뼈대가 같은 글이 매일 쌓인다(종목 20개를 같은 템플릿으로 찍으면 기계 눈에는 복제) ② 내용 없는 날의 글 — 주말 NVDA "휴장", 이벤트 0건인 날의 고정 문장만 있는 글 ③ 해석(입장)이 없다 — 전부 "관찰됐다" 어법의 서술이고, 세 리포트를 가로질러 읽는 글이 없다.

효과 있는 순서:
1. **빈 글은 올리지 않는다** — 이벤트 · 신호가 있는 날만. 자동, 비용 0. NVDA 주말(공시 · 뉴스만) 글도 이벤트 0건이면 건너뛴다
2. **고정 문장 · 섹션은 내용이 없으면 통째로 생략** — "오늘 주제에서는 … 없다" 같은 문장을 넣는 대신 섹션을 뺀다
3. **관전평** (7절) — 세 리포트를 가로질러 입장을 내는 칸. AI 가 매일 쓰고 사람 메모는 선택. 판별 주체는 사람 · AI 를 구분하지 못하고 글의 내용 · 조합이 새로운지만 본다 (2026-10-16 사용자 지적으로 "사람이 써야 한다"는 전제를 지움)
4. 개별 종목 리포트만 "승인 후 게시"로 두는 것도 가능하지만 완전 자동을 포기하는 비용이 커서 하지 않는다

## 7. 관전평 — 리포트를 가로지르는 해석 칸 (AI 기본 · 사람 메모 선택)

(2026-10-16 사용자: "너는 왜 관전평을 못 쓰는 거지?" — 맞는 지적. 판별 주체는 사람 · AI 를 구분하지 못하고 이름도 증명이 아니다. 차이는 누가 썼느냐가 아니라
**재료와 과제**다. 지금 서술은 리포트 하나 안의 데이터를 "관찰됐다" 어법으로 정리하는 과제라 같은 재료로 한 칸 더 쓰면 새 정보가 없다. 과제를 바꾸면 다른 글이 된다.)

**무엇**: 매일 AI 가 쓰는 관전평 3~5문장 + 사용자가 원하는 날 덧붙이는 메모. 리포트 머리에 "AI 관전평" 라벨 · 모델명과 함께. 사람 메모는 같은 칸 아래 사용자 이름으로.

**서술과 다른 점 — 과제 정의**
| 축 | 지금 서술 | 관전평 |
|---|---|---|
| 재료 | 리포트 하나의 분석값 | **세 리포트**(데일리 시장 상태 · 트럼프 이벤트와 robust 반응 · NVDA 이벤트 · 신호) + **최근 5일 관전평과 그 뒤 실제 움직임** |
| 과제 | 관찰 정리, 예측 · 원인 단정 금지 | **입장**: "이렇게 본다 — 이유 — 틀렸다고 볼 조건". 시나리오 어법 ("…이면 …로 본다") |
| 시간 | 오늘 | 어제 관전평 점검("맞았다 / 틀렸다 / 아직") + 오늘 입장 |

**출력 (JSON, 파이썬이 조립)**
- `review`: 어제 관전평 점검 1문장 — 파이썬이 채점 가능한 것(티커 · 방향이 있는 입장)은 가격으로 채점해 모델에 준다, 나머지는 모델이 판단
- `stance`: 1~2문장
- `reasons`: 2~3개, 각각 어느 리포트의 어느 값이 근거인지(숫자는 `fact_check` 대상)
- `invalidation`: 1문장 — "이 조건이면 틀린 것"
- 금지: 매수 · 매도 권유, 확정 예측("오를 것"). 시나리오 · 조건문으로만. 길이 상한

**언제 · 어디서 만드나**
- 세 리포트가 다 돈 뒤 — NVDA 실행 끝(뉴욕 17:30 + 몇 분)에 독립 단계로. 데일리 · 트럼프 상태는 브랜치에서 읽는다 (레이더가 생기면 레이더 실행 끝)
- 넣는 곳: **데일리 글 머리 카드**(Blogger API 로 갱신 — 데일리는 이미 게시된 뒤) · 홈 카드 · 레이더 글 머리(생기면). NVDA · 트럼프 글에는 안 넣는다(중복)
- 사슬: flash → lite → DeepSeek (`json`). 하루 1회

**기억**: `report-state` 에 `editor_notes.jsonl` — 날짜 · stance · invalidation · 근거 · 모델 · 다음 날 채점(파이썬 자동 / 모델 판단 구분). 최근 5일을 프롬프트에 넣는다. 30일이 쌓이면 "관전평 적중" 통계를 리포트 하단에 (성적표 — 알파 종목 리포트 4절과 같은 사고)

**사람 메모 (선택)**
- 입력 페이지: 블로그 Google 로그인(댓글) 재사용, 주인 UID 만. 날짜 · 대상 · 본문 300자
- 저장: Firestore `editor_notes/{YYYY-MM-DD}`. 쓰기 주인만, 읽기 서비스 계정만
- 반영: 5분마다 도는 댓글 봇에 동기화 단계 — 새 메모를 해당 글의 `data-editor-note` 자리에 Blogger API 로 넣는다. 수정 · 삭제도 같은 경로
- 쓰지 않은 날은 흔적 없음("메모 없음" 고정 문장 금지)

**표시 규칙**
- "AI 관전평 · gemini-3.5-flash" 처럼 모델명 명시(분류 표기와 같은 방식). 사용자 이름을 AI 글에 붙이지 않는다 — 검색엔진 때문이 아니라 독자 신뢰
- 사람 메모는 배경 없는 인용 표시 + 이름 + 시각
- 면책 문구는 그대로

**효과의 한계**: 검색엔진이 공개한 기준은 "가치"뿐이고, 관전평이 효과를 내는지는 유입 · 체류로만 확인된다. 보장은 없다. 6절 1 · 2번(빈 글 안 올리기 · 빈 섹션 생략)과 같이 가야 한다.

**작업량**: 관전평 생성 단계(프롬프트 · 채점 · 상태) 하루, 데일리 글 갱신 · 홈 카드 반나절, 사람 메모 경로 하루(선택)

## 8. 열린 질문

- 레이더 한 편에 종목 20개 카드가 들어가면 길이가 어떻게 되나 — 모바일에서 "조용한 종목" 접기
- 종목 라벨 페이지에 레이더 글도 보이게 할지(라벨 20개 달기 — 블로거 글당 라벨 한도 확인) 아니면 개별 리포트만
- 개별 리포트 상한 3편이 적정한지 — 실적 시즌에는 몰린다
- 레이더 서술을 종목별 한 줄로 할지(flash 20회 → 한도 초과) 섹터별 묶음 서술로 할지 — 묶음이 기본
- 유료 Tier 1 전환 시점
