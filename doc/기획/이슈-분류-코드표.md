# 이슈 분류 코드표 — 매일 기사를 저장할 때 붙이는 분류와 속성

작성: 2026-10-21 · 계기: 사용자 "미디어 기사를 매일 분류해 저장하고, 나중에 이슈와 종목 가격 변동의 통계를 내고 싶다 — 분류는 적게가 좋은가 넓게가 좋은가"
· 바탕: [데이터-기록-계획](데이터-기록-계획.md)(우리만의 데이터), [볼린저-이슈별-검증-계획](../검증/볼린저-이슈별-검증-계획.md)(30년 사건표 어휘 `experiments/issue_store/event_vocab.py`)
· 성격: 결론 정리 + **2026-10-21 밤 적용**(사용자: "우선 네가 정리하는 방향으로 진행, 미디어 쪽 분류 체계를 나중에 보여 주면 한 번 더 고친다").
  열린 질문(5절)은 Claude 가 정함: 미중 = 국가 속성 · 투자자 매매 · 의견 = INVESTOR_CALLS 코드(18개째) · 놀람 = 당장 모델, 나중에 캘린더 예상치 계산.

## 0. 결론 — 분류 수가 아니라 층이 답이다

- **큰 분류(코드 17개)** 는 통계용. 매일 쌓이면 1년에 코드마다 수백 건이 되어 비교가 된다.
- **세부 주제는 고정 어휘가 아니라 짧은 명사구**("인도산 2차 관세" · "메모리 반도체 가격")로 저장. 인물 발언 레이더의 `subtopic` 과 같은 방식.
  지금 고정하면 10년 뒤 세상이 바뀌었을 때 틀이 안 맞고, 자유로 두면 언제든 다시 묶을 수 있다.
- **분류보다 속성이 중요하다.** 30년 검증에서 배운 것: 주제만으로는 방향이 안 나온다(같은 "금리"라도 인상 신호와 인하 기대는 반대). 방향 · 놀람 · 범위 · 대상 · 강도를 같이 저장해야 10년 뒤 통계가 된다.
- **세 곳이 한 어휘를 쓴다.** 공용 뉴스 분류(종목 레이더) · 데일리 CNBC 뉴스 · 인물 발언 레이더 · 30년 사건표. 과거 자료와 앞으로 쌓이는 자료를 나중에 이어 붙이려면 어휘가 같아야 한다.

## 2. 속성 — 기사마다 같이 저장하는 것

| 속성 | 값 | 왜 필요한가 |
|---|---|---|
| issue | 1절 코드 하나 | 통계 묶음 |
| subtopic | 짧은 명사구(영어 2~4 단어, 화면은 한국어 캐시) | "무엇"을 남긴다. 나중에 다시 묶는 재료 |
| direction | positive · negative · uncertain · neutral | 같은 코드 안에서 방향이 갈린다 |
| scope | market · sector · stock | 시장 전체 뉴스와 한 종목 뉴스는 다른 통계 |
| targets | tickers[] · sectors[] · countries[] | 대상. 빅테크 · 미중 같은 구분은 여기서 나온다 |
| scheduled | true · false | 예정 발표(CPI · FOMC · 실적)와 돌발 사건은 반응 구조가 다르다 |
| surprise | -2 ~ +2 (예상보다 훨씬 나쁨 ~ 훨씬 좋음), 모르면 0 | 예정 발표는 "예상 대비"가 전부. 돌발은 0 |
| intensity | 1 ~ 10 | 인물 발언 · 트럼프와 같은 자 |
| n_sources | 보도 매체 수 | 시장이 얼마나 주목했나의 대리 값 |
| first_seen · last_seen | 시각 | 며칠째 이어지는지(지속)는 저장이 아니라 계산 |
| lead_of_day | true · false (하루 한 건) | 그날 가격을 움직인 주도 이슈 표시 — 하루에 이슈가 여럿일 때 분류만으론 못 가린다 |
| price_reaction | 저장 시점의 그날 반응 (지수 · 대상 종목의 1일 수익률, 평소 범위 대비 배수) | [데이터-기록-계획](데이터-기록-계획.md) 2부 규칙 |

관련도(relevance 0~3)와 기업 영역(area)은 지금 공용 뉴스 분류에 있는 그대로 둔다. 기업 영역(실적 · 수급 · 규제 · 법적 · 제품 · 수요 · 공급 · 기업 · 거시)은 "그 회사에 무슨 일"이고, 이슈 코드는 "세상에 무슨 일"이라 축이 다르다. 둘 다 저장한다.

## 3. 지금 있는 어휘와의 대응

### 3-1. 30년 사건표 세부 종류 21개 (`event_vocab.py`) → 이슈 코드

### 3-2. 인물 발언 레이더 주제 19개 → 이슈 코드
Trade → TARIFF_TRADE · Fed → RATES_FED · Tax → FISCAL_POLITICS · Energy → OIL_ENERGY · Immigration → GROWTH_JOBS(노동 공급) · Regulation → REGULATION · Geopolitics → GEOPOLITICS · Company / Product / Deal / Investment → CORP_EVENT · Stock Call / Sector Call / Position → MARKET_STRUCTURE(투자자 매매 · 의견은 수급) · Macro Warning / Market Outlook → 내용에 따라(거품 → AI_CAPEX, 침체 → GROWTH_JOBS, 그 밖 MARKET_STRUCTURE) · Earnings → EARNINGS · Industry View → AI_CAPEX 또는 해당 섹터 · Policy → FISCAL_POLITICS
인물 발언의 주제 enum 은 그대로 두고 **이슈 코드를 한 칸 더** 붙인다(인물군별 주제는 발언 분석에 맞게 만든 것이라 없애면 손해).

### 3-3. 공용 뉴스 분류 기업 영역 10개 (`stock-radar/prompts/classify.txt`)
축이 다르므로 대응표 없음. 기사마다 area(기업 영역) + issue(이슈 코드) 둘 다.

### 3-4. 홈 실시간 뉴스의 글자 규칙 분류(AI · 금리 · 에너지 …)
LLM 없이 제목 단어로 나누는 임시 규칙. 공용 분류가 이슈 코드를 갖게 되면 그 값을 읽는다.

## 4. 분류 수에 대한 판단 근거

- 코드 17개 × 방향 4 × 범위 3 = 204칸. 하루 50~100건이면 한 달에 큰 칸은 수십 건, 1년이면 작은 칸도 찬다.
- 더 잘게 나누면(사용자 걱정 "원인을 자세히") 칸이 비고 분류 일관성이 떨어진다(경계 사례가 늘어 모델이 흔들린다). 그 역할은 subtopic 이 맡는다.
- 더 줄이면(8개 안팎) 통계는 빨리 차지만 "무엇 때문에"가 사라진다. 속성(대상 · 세부 주제)이 있어도 코드가 너무 넓으면 같은 칸에 반대 현상이 섞인다 — 30년 검증의 평균의 함정.
- 17개는 사건표 7대분류와 21세부의 중간이다. 10년 뒤에도 쓰려면 "세상이 바뀌어도 남는 축"(금리 · 물가 · 경기 · 무역 · 지정학 · 에너지 · 실적 · 규제 · 재정 · 신용 · 수급 · 환율 · 부동산)이어야 하는데, AI_CAPEX · CRYPTO 둘만 시대 테마다. 테마가 식으면 OTHER 로 흡수하고 코드는 남겨 둔다(과거 자료 호환).

## 5. 열린 질문 (사용자 결정)

1. US_CHINA 를 코드로 둘지, 국가 속성으로 풀지 — 이 문서는 속성 쪽. 미중 관계를 한 칸으로 자주 보고 싶으면 코드로 둔다.
2. 투자자 매매 · 종목 의견(인물 발언의 Position · Stock Call)을 MARKET_STRUCTURE 에 넣을지, OPINION_FLOWS 코드를 따로 만들지.
3. surprise(-2~+2)를 모델에게 맡길지, 예정 발표만 사람이 캘린더 예상치와 대조해 계산할지 — 정확하려면 후자, 당장은 전자.
